# 도메인 관계 및 업무 규칙

현재까지 논의한 도메인 관계와 확정한 상태 정책을 기록합니다.
MVP의 테이블·컬럼·키 기준은 [확정 ERD](erd.md)에 기록합니다. JPA 매핑과 API는 후속 설계합니다.

## 도메인별 책임

| 도메인 | 책임 |
| --- | --- |
| User | 사용자 계정 정보와 서비스 전체 역할 관리 |
| Club | 동아리 기본 정보, 운영 상태와 모집 정보 관리 |
| ClubManager | 특정 사용자와 특정 동아리 사이의 관리 권한 관계 |
| ClubMember | 사용자·동아리의 가입 상태와 승인 운영자 관리 |
| Activity | 동아리 활동 내역과 실제 활동일 기록 |
| Notice | 동아리 공지사항 관리 |
| Gathering | 일반 사용자가 주최하는 동아리와 독립된 일회성·기간제·정기 소모임 |
| GatheringParticipant | 고정 멤버 방식의 모임 가입 신청·확정 상태 |
| GatheringSession | 실제 개최 회차의 일정·장소·정원·모집·취소 |
| GatheringSessionParticipant | 회차별 참여 상태 및 출결 |
| ActivityParticipant | 동아리 활동의 참가자 명단 및 출결 |

일반 회원가입 없이 42 인증 후 최초 로그인 시 User를 생성합니다. 42 고유 사용자 ID로 중복을 방지하며 최초 역할은 일반 사용자입니다.
일반 교육생과 운영진은 모두 같은 User로 관리하며 User.role의 USER / ADMIN으로 서비스 역할을 구분합니다. ClubManager는 별도의 계정이나 동아리 회원 명단이 아닙니다.
MVP에서는 모집 정보를 Club에 포함하고 별도의 모집 회차 도메인은 만들지 않습니다.
동아리 가입 관계는 ClubMember로 설계하며 가입·탈퇴 상태를 관리합니다. 가입 관계와 API는 아직 미구현입니다. 활동보고, 사진, 결제는 현재 범위에서 제외합니다. 활동별 참가자 명단과 소모임 내부 참여 신청은 포함합니다.

## 사용자 이용 자격 및 정보 정리

- 사이트 자체에서 사용자가 요청하는 계정 탈퇴 기능은 구현 범위에서 제외합니다. 소모임 탈퇴·회차 참여 취소·동아리 관리자 권한 해제와 구분합니다.
- 42 API로 사용자의 블랙홀 진입이 확인되면 서비스 DB에서 해당 사용자 정보를 삭제하는 방향으로 진행합니다. 계정 탈퇴 요청을 삭제 조건으로 사용하지 않습니다.
- 사용자 정보 정리 이후에도 과거 기록에는 기존 아이디를 표시하는 방향으로 진행합니다. 보존할 아이디의 종류(Intra 로그인명 또는 내부 사용자 ID)와 저장 방식은 후속 확정하며, 일괄적으로 삭제된 사용자라는 표시로 바꾸지 않습니다.
- 블랙홀 판정은 실제 42 응답과 대상 cursus의 의미를 검증한 뒤 확정합니다. API 호출 실패·응답 누락이나 blackholed_at 값의 존재만으로 사용자 삭제를 실행하지 않습니다.
- 사용자 행의 물리 삭제 범위, 기존 작성·주최·참가·출결 참조 처리, 주최 중인 활동·소모임 처리, 확인 주기 및 재로그인 시 계정 생성 방지는 후속 결정 사항입니다. 기존 기록 보존 정책과 모순되지 않도록 함께 설계합니다.

### 42 API 확인 현황

- [Auth.js 42 제공자 소스](https://github.com/nextauthjs/next-auth/blob/main/packages/core/src/providers/42-school.ts)는 사용자 프로필의 cursus_users에 blackholed_at(문자열 또는 NULL)을 정의합니다. 이 자료만으로 실제 블랙홀 진입 판정식을 확정할 수는 없습니다.
- [42 사용자 조회 공식 문서](https://api.intra.42.fr/apidoc/2.0/users/show.html)는 이번 확인에서 인증 화면으로 전환되어 내용을 확인하지 못했습니다. 실제 연동 시 응답 및 예외 조건을 검증해야 합니다.

## 관계도

[README ERD](../README.md#erd)에서 전체 관계를, [ERD 명세](erd.md)에서 컬럼과 제약조건을 확인합니다.

## 사용자 역할과 동아리 관리 권한

| 구분 | 표현 | 권한 범위 |
| --- | --- | --- |
| 일반 교육생 | User.role = USER | 공개 정보 조회, 로그인 후 소모임 생성·참여 신청 |
| 운영진 | User.role = ADMIN | 동아리 생성, 운영 상태 관리, 관리자 지정·변경, 회원 가입 승인 |
| 동아리 관리자(회장) | 해당 동아리의 ClubManager 관계 | 동아리 소개·모집 정보와 활동·공지 관리 |

공개 조회만 하는 방문자를 위해 계정을 생성할 필요는 없습니다.
회장은 해당 동아리의 ClubManager 관계를 가진 사용자로 표현하며 별도 회장 계정·테이블·전역 역할을 만들지 않습니다. USER와 ADMIN 모두 ClubManager가 될 수 있고 동아리 관리 권한은 동일합니다.
ADMIN이면서 ClubManager인 사용자는 운영진 권한과 해당 동아리 관리 권한을 함께 가집니다.
운영진도 해당 동아리의 ClubManager로 지정되어야 소개·모집 정보·활동·공지를 등록하거나 수정할 수 있습니다. 운영진 역할만으로 해당 권한을 부여하지 않습니다.
활동의 참가자·출결 관리 권한은 별도로 현재 지정된 주최자를 기준으로 검사합니다.

### ClubManager 규칙 — 확정

- 한 사용자가 여러 동아리를 관리할 수 있습니다.
- 한 동아리에 여러 관리자를 허용합니다.
- 관리자가 없는 동아리의 생성과 유지를 허용합니다.
- 각 ClubManager는 반드시 사용자 한 명과 동아리 한 개에 연결됩니다.
- 동일한 사용자·동아리 조합을 중복 등록할 수 없습니다.
- ERD에는 필수 사용자·동아리 참조와 `(user_id, club_id)` 복합 유니크 제약조건을 반영합니다.
- 운영진이 관계를 생성하거나 제거하여 권한을 부여·해제합니다.
- 마지막 관리자의 권한도 해제할 수 있습니다. 동아리와 기존 활동·공지는 유지합니다.
- 관리자 부재만으로 운영 상태나 공개 여부를 자동 변경하지 않습니다.
- 현재 설계에서는 관리자 사이에 대표자·부관리자 등 별도 권한 등급을 두지 않습니다.

ClubManager는 권한을 기록하고, 서비스 로직은 로그인 사용자와 대상 동아리의 관계를 확인해 요청을 허용하거나 거부합니다.
전역적인 동아리 관리자 역할 하나만으로 리소스 접근을 허용하지 않습니다.

### 작성자와 수정 권한 — 현재 설계 방향

- Activity와 Notice의 작성자는 ClubManager가 아닌 User에 연결합니다.
- 작성자는 누가 등록했는지 기록하기 위한 정보입니다.
- 수정·삭제 권한은 작성자 여부보다 해당 동아리의 현재 관리 권한을 기준으로 검사합니다.
- 새 관리자는 기존 관리자가 작성한 활동·공지도 관리할 수 있습니다.
- 관리 권한 해제 후에도 기존 작성자 정보와 게시물을 유지합니다.
- 블랙홀에 따른 사용자 정보 삭제 시 기존 작성 기록의 사용자 참조를 처리하는 구체적인 방식은 별도 결정합니다.

## 동아리 가입 한도 — 확정

- 사용자당 활성 동아리의 동시 가입은 정책상 최대 2개입니다. 가입 승인은 ADMIN 권한을 가진 운영자가 담당하며 이 한도를 확인하고 승인 여부를 판단합니다.
- 가입 관계는 ClubManager 관리 권한과 별도로 관리합니다. 관리 권한 부여만으로 회원 가입을 자동 생성하거나 가입 수를 증가시키지 않습니다.
- 승인 화면에서 대상 사용자의 현재 가입이 확정된 동아리 목록과 개수를 승인 대상 옆에 표시합니다. 동아리 이름·ID를 제공하여 운영자가 기존 가입 관계를 확인할 수 있도록 합니다.
- 가입 동아리 수에 따른 자동 거절이나 등록 시 자동 한도 검사를 두지 않습니다. 시스템의 강제 차단 대신 운영자가 표시된 가입 내역으로 확인하는 방식입니다. ADMIN 승인 권한 검증은 별도로 적용합니다.
- 동아리 관리자(ClubManager)는 관리 권한만으로 가입을 승인할 수 없습니다. ADMIN 권한도 가진 경우에는 운영자 자격으로 승인할 수 있습니다.
- 외부 지원·모집 안내를 유지하고 ADMIN 운영자가 외부 결과를 확인하여 서비스에 가입을 등록합니다. 사이트 내부 동아리 가입 신청·승인 대기·거절 기능은 두지 않습니다.
- 아카이브 시 기존 ACTIVE 가입 관계를 모두 LEFT로 전환하므로 최대 2개 가입 한도에서 제외됩니다. 가입 관계 자체는 보존하며 구체적인 전환 규칙은 [아카이브 정책](#게시-및-아카이브-정책--확정)을 따릅니다. 한도에는 ClubMember.status = ACTIVE이면서 Club.operationStatus = ACTIVE인 관계만 포함합니다.
- 탈퇴 승인 주체·처리 시점, 아카이브 상태의 가입 등록·재가입 가능 여부 및 블랙홀 이후 가입 관계 처리는 후속 결정합니다.

### 동아리 가입 관계 — 확정

- ClubMember는 사용자와 동아리 사이의 가입 관계이며 ACTIVE(가입 중)와 LEFT(탈퇴) 두 상태를 사용합니다. 동아리 자체의 운영 상태와 구분합니다.
- ADMIN 운영자의 최초 가입 등록으로 ACTIVE 관계를 생성하고 승인 운영자·가입 시각을 기록합니다. 회원 등록이 관리자 권한을 부여하지는 않습니다.
- 탈퇴 완료는 관계를 물리 삭제하지 않고 LEFT로 변경하며 탈퇴 시각을 기록합니다. 탈퇴 신청은 완료와 구분하며 아래 보류 정책을 따릅니다. 동아리 탈퇴는 사이트 계정 탈퇴와 구분합니다.
- 재가입은 ADMIN 운영자의 승인으로 기존 LEFT 관계를 ACTIVE로 변경하고 승인 운영자·가입 시각을 갱신하며 탈퇴 시각을 비웁니다.
- 동일한 사용자·동아리 조합에는 관계 하나만 유지하여 중복 가입을 방지합니다.
- 승인 화면에는 ACTIVE인 가입 관계의 동아리 목록과 각 동아리의 운영 상태를 표시하며, 한도에 포함되는 활성 동아리 가입 수를 제공합니다. 아카이브로 LEFT가 된 관계를 포함하여 모든 LEFT 관계는 현재 가입 목록과 한도에서 제외합니다. 과거 가입·탈퇴 기록은 DB에 보존합니다.

### 동아리 탈퇴 신청·승인 — 승인 정책 보류

- 동아리 탈퇴 신청은 가입한 사용자 본인이 합니다. 인증 정보로 본인을 식별하며 다른 사용자 대신 신청하는 기능은 두지 않습니다.
- 탈퇴 승인이 필요한 방향으로 진행하되 승인 주체는 회장 또는 ADMIN 운영자 중 미정이며 보류합니다. 가입 등록을 ADMIN이 담당한다는 이유만으로 탈퇴 승인 권한도 자동 부여하지 않습니다.
- 회장 승인 방식을 선택하면 해당 동아리의 현재 ClubManager 관계로 승인 권한을 판단합니다. USER / ADMIN 구분과 별개이며 추가 회장 모델은 필요하지 않습니다. 어느 승인 방식을 적용할지는 계속 보류합니다.
- 아카이브에 따른 일괄 탈퇴는 운영진의 상태 변경 효과이며 본인의 탈퇴 신청·승인 절차와 별개로 적용합니다.
- 신청만으로 즉시 LEFT로 전환하는 본인 탈퇴 API는 구현하지 않습니다. 승인 주체·승인/거절·신청 취소·신청 저장 구조·처리 시점은 후속 확정하고 탈퇴 신청·승인 API 구현은 보류합니다.

## 소모임 및 출결

### 소모임 관계와 권한 — 확정

- Gathering은 일회성·기간제·정기 모임을 지원하며 Club·ClubManager와 연결하지 않습니다.
- 로그인한 일반 사용자가 생성하며 생성자가 주최자입니다. 주최자는 자신의 모임 정보·모집·승인을 관리합니다.
- 소모임은 동아리 활동도에 포함하지 않습니다.
- 주최자는 생성 시 FIRST_COME(선착순 즉시 확정) 또는 APPROVAL(승인제)을 선택합니다.
- 총정원에 주최자를 포함합니다. 고정 멤버 방식은 모임 생성 시 주최자의 가입 관계를, 두 방식 모두 회차 생성 시 주최자의 회차 참여 관계를 CONFIRMED로 생성합니다.
- 정원은 CONFIRMED 인원으로 계산하며 PENDING은 자리를 예약하지 않습니다.
- 선착순 신청·재신청 시, 승인제 승인 시 잔여 정원을 검증합니다. 동시 요청에서도 정원을 초과하지 않아야 합니다.
- 주최자는 개별 참여 취소가 불가능하며 모임 전체를 취소해야 합니다.
- 모임 전체 취소와 개인의 신청 취소는 구분합니다. 취소된 모임은 신청·승인을 받지 않으며 참가자를 자동으로 결석 처리하지 않습니다.

### 신청 상태와 재신청

| 상태 | 의미 |
| --- | --- |
| PENDING | 승인 대기 |
| CONFIRMED | 참여 확정 |
| REJECTED | 주최자가 거절 |
| CANCELLED | 사용자가 신청·참여 취소 |

- FIRST_COME 신청은 정원 내에서 CONFIRMED, APPROVAL 신청은 PENDING으로 시작합니다.
- 승인제의 PENDING은 주최자 승인 시 CONFIRMED, 거절 시 REJECTED로 변경합니다.
- 일반 참가자는 PENDING·CONFIRMED 상태에서 본인 신청을 CANCELLED로 변경할 수 있습니다. 주최자는 예외입니다.
- REJECTED·CANCELLED에서 재신청을 허용하며 기존 관계를 재사용합니다.
- 재신청도 현재 신청 방식과 모집 조건을 따릅니다. PENDING·CONFIRMED의 중복 신청은 거절합니다.
- 고정 멤버 가입은 UNIQUE(gathering_id, user_id), 회차 참여는 UNIQUE(session_id, user_id)를 유지합니다.
- 신청 방식 변경은 주최자 외 신청 이력이 생긴 후 금지하는 방향입니다. 주최자 자동 등록을 최초 신청으로 취급하면 생성 직후부터 변경이 불가능하므로 제외합니다.
- 별도 빈자리 대기열은 만들지 않습니다. PENDING은 주최자의 승인을 기다리는 상태입니다.

### 동아리 활동 주최자 — 확정

- Activity의 최초 작성자(author_id)와 주최자(organizer_id)를 분리합니다. 같은 사용자여도 됩니다.
- 동아리 관리자가 활동 등록·수정과 주최자 지정을 담당합니다.
- 가입된 일반 User도 주최자가 될 수 있으며 ClubManager 권한이 필요하지 않습니다.
- 지정된 주최자는 해당 활동의 참가자 명단과 출결을 관리합니다.
- 현재 지정된 활동 주최자는 본인의 ActivityParticipant 출결도 직접 체크·정정할 수 있습니다. 본인 출결에도 마지막 체크 사용자와 시각을 기록하며, 주최자 변경 후에는 새 주최자가 기존 주최자의 출결을 관리합니다.
- 주최자 지정은 다른 활동이나 동아리 소개·모집 정보를 수정할 권한을 주지 않습니다.
- 활동 생성 시 지정된 주최자의 ActivityParticipant를 같은 트랜잭션에서 자동 생성합니다. 출결은 UNCHECKED로 시작하며 자동 참가를 자동 출석으로 처리하지 않습니다.
- 그 외 참가자는 주최자가 ActivityParticipant에 등록합니다. 동아리 회원 명단이나 소모임 신청 절차와 구분합니다.
- UNIQUE(activity_id, user_id)로 참가자 중복을 방지합니다.

#### 활동 주최자 변경 — 확정

- 활성 동아리의 현재 관리자가 주최자를 변경할 수 있습니다. 아카이브 상태에서는 기존 변경 제한에 따라 허용하지 않습니다.
- 새 주최자가 참가자로 등록되어 있지 않으면 ActivityParticipant를 자동 생성하고 출결을 UNCHECKED로 설정합니다. 이미 참가자라면 기존 관계와 출결을 그대로 유지하며 중복 등록하지 않습니다.
- 기존 주최자는 참가자로 남으며 기존 출결·마지막 체크 사용자·시각을 보존합니다. 주최자 변경만으로 참가 관계를 제거하거나 출결을 초기화하지 않습니다.
- 참가자 명단·출결 관리 권한은 변경 완료 시 새 주최자에게 이전합니다. 기존 주최자는 주최자 지위에 따른 관리 권한을 잃습니다.
- 최초 작성자(author_id)는 변경하지 않습니다.
- 주최자 변경과 새 주최자의 필요한 참가 관계 생성은 같은 트랜잭션에서 처리합니다.

### 출결 — 공통 설계

| 상태 | 의미 |
| --- | --- |
| UNCHECKED | 미확인, 기본값 |
| PRESENT | 출석 |
| LATE | 지각 |
| ABSENT | 결석 |

- 신청 상태와 출결 상태는 별개입니다. 미확인을 결석으로 간주하지 않습니다.
- 소모임은 CONFIRMED 참가자만 출결 대상이며 주최자도 포함됩니다.
- 동아리 활동은 등록된 ActivityParticipant를 대상으로 합니다.
- 각 모임·활동의 지정된 주최자가 출결을 체크합니다. ClubManager만으로 출결 수정 권한을 얻지는 않습니다.
- ActivityParticipant와 GatheringSessionParticipant에 출결 상태, 마지막 체크 사용자와 시각을 기록합니다. 변경 이력 전체를 저장하는 설계는 아닙니다.
- 취소 회차에는 신규 출결을 기록하지 않습니다.
- 모임 전체 취소는 출결과 분리하며 기존 출결을 일괄 결석으로 덮어쓰지 않습니다.

## 운영 상태와 활동도 — 확정

운영 상태와 활동도는 서로 다른 정보입니다.

| 항목 | 값 | 결정 방식 |
| --- | --- | --- |
| 운영 상태 | 활성(ACTIVE) / 아카이브(ARCHIVED) | 운영진이 직접 변경 |
| 활동도 | 활발 / 보통 / 활동 기록 부족 | 최근 90일의 실제 활동일을 기준으로 계산 |

- 운영 상태는 활성과 아카이브 두 가지로만 구분하며 휴면 상태를 두지 않습니다. 활동이 적다는 이유로 운영 상태를 자동 변경하지 않습니다.

### 활동도 계산

| 최근 90일 활동 건수 | 표시 |
| --- | --- |
| 3건 이상 | 활발 |
| 1~2건 | 보통 |
| 0건 | 활동 기록 부족 |

- 게시물 등록일 대신 Activity의 실제 활동일을 사용합니다.
- 조회 시점의 한국 날짜(`Asia/Seoul`)를 오늘로 삼아 오늘−89일부터 오늘까지 양 끝 날짜를 포함한 90일을 집계합니다. 오늘−90일의 활동은 제외하고 오늘의 활동은 포함합니다.
- 공지사항·소모임·미래 활동은 집계에서 제외합니다.
- 활동도가 낮아져도 운영 상태를 자동으로 변경하지 않습니다.
- 화면에는 `최근 90일 실제 활동일 기준`을 안내합니다.
- 기록이 없다는 이유만으로 실제 활동이 없다고 단정하지 않습니다.
- 활동도는 별도 저장 값 대신 조회 시 현재 저장된 활동일로 계산합니다. 활동일 수정이 완료되면 다음 조회부터 변경된 날짜가 집계에 즉시 반영됩니다.
- [삭제된 활동](#활동공지-삭제와-기록-보존--확정)은 집계에서 제외합니다. 삭제가 완료되면 다음 조회부터 활동도에 즉시 반영됩니다.

## 모집 정보와 상태 — 확정

Club에 모집 계획 여부, 시작일, 종료일, 조기 마감 여부 및 지원 방법을 관리합니다.
지원은 외부 안내 경로로 진행하며, 서비스 내부 지원서 접수는 MVP에서 구현하지 않습니다.

표시용 모집 상태는 다음 순서로 계산합니다.

| 우선순위 | 조건 | 상태 |
| --- | --- | --- |
| 1 | 모집 계획 없음 | 모집 안 함 |
| 2 | 조기 마감 처리됨 | 마감 |
| 3 | 시작일 전 | 모집 예정 |
| 4 | 종료일이 있고 종료일이 지남 | 마감 |
| 5 | 위 조건에 해당하지 않음 | 모집 중 |

- 모집 계획이 있는 경우 시작일은 필수입니다.
- 종료일이 없으면 시작일부터 상시 모집합니다.
- 종료일은 시작일보다 빠를 수 없습니다. 같은 날 시작하고 종료할 수 있습니다.
- 한국 시간(`Asia/Seoul`) 기준으로 시작일 당일부터 종료일 당일까지 모집 중입니다.
- 일정 종료 전에도 수동으로 조기 마감할 수 있습니다.
- 표시용 모집 상태는 조회 시 계산하여 날짜와 상태가 불일치하지 않도록 합니다.
- 모집 회차별 이력은 MVP에서 관리하지 않습니다.

### 모집 계획 취소 — 확정

- 모집 계획 취소는 동아리 모집 자체를 진행하지 않기로 하고 모집 계획 여부를 false로 변경하는 것입니다. 표시 상태는 모집 안 함(NOT_RECRUITING)이 됩니다.
- 취소할 때 시작일·종료일·지원 방법·지원 링크를 모두 비우고 조기 마감 여부를 false로 초기화합니다. 모집 계획 변경과 값 초기화는 한 트랜잭션에서 처리합니다.
- 기존 모집 값을 숨겨서 보관하거나 다음 모집에 자동 복원하지 않습니다. 새 모집은 필요한 정보를 다시 입력해야 합니다.
- 조기 마감은 모집 계획과 안내를 보존하면서 마감하는 것으로, 모집 계획 취소와 구분합니다. 아카이브에 따른 마감도 계획 취소로 취급하지 않습니다.
- 취소 권한과 운영 상태에 따른 변경 제한은 모집 정보 수정에 적용되는 기존 정책을 따릅니다.

## 게시 및 아카이브 정책 — 확정

- 활동·공지는 임시저장 없이 등록 즉시 공개합니다.
- 동아리는 물리 삭제하지 않고 아카이브 상태로 보존합니다.
- 운영진만 아카이브·재활성화할 수 있습니다.
- 아카이브 동아리는 일반 목록에서 기본 제외하고 아카이브 목록에서 조회합니다. 기존 동아리 상세와 삭제되지 않은 활동·공지는 열람할 수 있습니다.
- 아카이브 상태에서는 모집할 수 없습니다. 모집 계획이 있으면 마감 처리하고, 없으면 모집 안 함을 유지합니다.
- 아카이브 전환 시 해당 동아리의 모든 ACTIVE ClubMember를 LEFT로 변경하고 left_at을 전환 시각으로 기록합니다. 승인 운영자·가입 시각·관계 최초 생성 시각은 보존하고 updated_at은 갱신합니다. 기존 LEFT 관계의 탈퇴 시각은 덮어쓰지 않습니다.
- 동아리 운영 상태 전환·모집 마감·회원 일괄 탈퇴는 같은 트랜잭션에서 처리하여 일부만 반영되지 않도록 합니다.
- 기존 활동 참가자·출결 기록은 회원 탈퇴와 별개로 보존합니다.
- 재활성화 시 동일한 동아리 ID와 과거 기록을 유지하되 기존 LEFT 회원을 자동으로 재가입시키지 않습니다. 다시 가입하려면 ADMIN의 재가입 등록이 필요합니다.
- 기존 관리 권한은 자동 삭제하지 않으며 운영진이 검토·변경합니다. 재활성화에 관리자를 필수로 요구하지는 않습니다.
- 운영 중으로 전환해도 과거 모집은 자동으로 다시 열리지 않습니다. 관리자가 새 모집 정보를 설정해야 합니다.
- 새 기수는 우선 관리자 변경과 새 모집으로 처리합니다. 별도 기수·아카이브 테이블은 만들지 않습니다.

### 상태별 변경 허용 범위 — 확정

| 대상 | 활성(ACTIVE) | 아카이브(ARCHIVED) |
| --- | --- | --- |
| 동아리 소개·기본 정보 | 해당 동아리 관리자가 수정 가능 | 수정 불가 |
| 모집 정보 | 해당 동아리 관리자가 설정·수정 가능 | 설정·수정 불가 |
| 활동·공지 | 해당 동아리 관리자가 등록·수정·삭제 가능 | 신규 등록·수정·삭제 불가 |
| 기존 활동의 참가자·출결 | 현재 지정된 활동 주최자가 관리 | 현재 지정된 활동 주최자가 정정 가능 |

- 아카이브 후에도 기존 공개 정보는 열람할 수 있으며 참가자·출결 명단은 기존 조회 권한을 유지합니다.
- 활동 주최자 변경은 활동 수정에 해당하므로 아카이브 상태에서는 허용하지 않습니다.
- 운영진이나 동아리 관리자라는 이유만으로 참가자·출결 정정 권한을 얻지 않습니다. 해당 활동의 현재 주최자여야 합니다.
- 참가자 제거 정책은 별도 확정 전까지 보류합니다. 아카이브 후 정정 허용이 게시물 삭제 권한을 추가하지는 않습니다. 삭제된 활동의 변경 제한은 아래 삭제 정책을 따릅니다.

### 활동·공지 삭제와 기록 보존 — 확정

- 활동·공지는 DB에서 물리 삭제하지 않고 삭제 시각을 기록하여 삭제됨으로 처리합니다. 일반 목록에서 제외하고 일반 상세 조회도 허용하지 않습니다.
- 활성 동아리의 현재 관리자가 삭제할 수 있습니다. 운영진도 해당 동아리의 관리자 권한이 필요하며, 최초 작성자라는 이유만으로 삭제 권한을 얻지 않습니다.
- 아카이브 상태에서는 활동·공지를 삭제할 수 없습니다. 삭제 복원은 MVP에서 지원하지 않습니다.
- 활동 삭제 시 참가 관계·출결·마지막 체크 사용자·시각을 그대로 보존합니다. 삭제 완료 후 활동 수정·주최자 변경·참가자 등록 및 출결 체크·정정은 차단합니다.
- 삭제된 활동의 참가·출결 기록은 본인의 참여 내역과 해당 활동의 현재 주최자 관리 화면에서만 조회할 수 있습니다. 일반 참가자는 다른 사람의 기록을 볼 수 없으며, 운영진·동아리 관리자 역할만으로 관리 명단을 조회할 수 없습니다.
- 삭제된 활동은 활동도 집계에서 즉시 제외합니다. 별도 기록 보존 기한이나 영구 파기 절차는 블랙홀에 따른 사용자 정보 정리 정책과 함께 후속 결정합니다.

## 일정·참여 단위 확장

진행 방식과 참여 단위, 확정 방식을 독립적으로 선택합니다.

| 축 | 값 | 의미 |
| --- | --- | --- |
| 목적·분류 | 스터디 / 프로젝트 / 해커톤·대회 / 친목 / 기타 (초안) | 모임의 목적 |
| 진행 방식 | ONE_TIME / FIXED_TERM / RECURRING | 일회성 / 기간제 / 정기 |
| 참여 단위 | PER_SESSION / FIXED_MEMBERS | 회차별 모집 / 고정 멤버 |
| 확정 방식 | FIRST_COME / APPROVAL | 선착순 / 승인제 |

- 반복 커피챗은 정기 일정과 회차별 모집, 대회 준비는 기간제와 고정 멤버를 조합할 수 있습니다.
- 기간제도 반복 일정을 가질 수 있습니다. 반복 규칙과 실제 회차는 별개로 저장합니다.
- 일회성도 실제 회차 하나를 사용합니다. 정기 모임의 예외 일정·휴회는 해당 회차에서 처리합니다.
- PER_SESSION은 회차마다 신청·정원·취소·출결을 관리합니다. 이전 회차 참가자에게 다음 자리를 자동 부여하지 않습니다.
- FIXED_MEMBERS는 모임에 한 번 가입하고 회차별 참가 대상과 출결을 관리합니다.
- 가입과 회차 참여는 별도 테이블로 분리합니다. session_id의 NULL 여부로 행의 의미를 바꾸는 통합 방식은 채택하지 않습니다.
- 불참·결석만으로 고정 멤버 자격을 자동 해제하지 않습니다. 지난 회차의 결석 자리를 소급 모집하지 않습니다.

### 모집 공개와 일정

- 모집은 대상 시작 시각 최소 2시간 전에 공개해야 합니다. 즉시 공개는 현재 시각, 예약 공개는 예약 시각을 기준으로 검증합니다.
- PER_SESSION은 각 회차 시작 시각, FIXED_MEMBERS의 최초 모집은 첫 회차 시작 시각을 기준으로 합니다.
- 공개 시각을 과거로 입력하여 제한을 우회할 수 없습니다. 공개·일정 변경 시 서버에서 재검증합니다.
- 신규 신청·재신청은 모집 마감 전까지, 회차 참여 취소는 시작 전까지 허용하는 방향입니다.
- 모집 마감은 시작 이전으로 설정하며 주최자의 조기 마감을 허용합니다.
- 이미 확정된 인원보다 정원을 줄일 수 없습니다.
- 정원이 찬 경우 신규 신청은 막고, 승인 대기는 유지합니다. 정원 검증은 승인 시에도 수행합니다.
- 회차 취소와 전체 모임 취소를 구분합니다. 전체 취소는 모든 미래 회차의 모집·개최를 중단하며 과거 출결은 보존합니다.
- 소모임 주최자는 MVP에서 변경하지 않습니다. 출결은 시작 이후 체크·정정하는 방향입니다.

### 동아리 적용 범위

동아리에도 목적·분류와 정기 일정 안내가 필요합니다. 지속되는 조직 자체를 일회성으로 취급하지 않습니다.
동아리 활동의 반복 묶음·기간제 구조는 별도 후속 설계이며, 현재 11개 테이블에는 소모임 회차 구조만 반영합니다.
동아리 분류와 정기 일정의 구조화 필드도 아직 확정하지 않았으며 요구사항을 삭제한 것이 아닙니다.

## 남은 결정 사항

- 동아리 탈퇴 승인 주체(해당 동아리 ClubManager 또는 ADMIN)·승인/거절·신청 취소·저장 구조·처리 시점 — 보류
- 아카이브 동아리의 가입 등록·재가입 허용 여부, 블랙홀 시 가입 관계 처리
- 블랙홀 이후 기록에 보존할 아이디의 종류와 저장 방식

- 목적 분류의 최종 목록, 반복 요일·간격·시간대의 표현과 회차 생성 범위
- 고정 멤버의 회차 명단 반영 시점, 한 회차 불참·탈퇴·중도 가입 규칙과 첫 회차 이후 추가 모집의 2시간 기준
- 소모임 전체 취소 후 복원 여부, 신청·승인 가능 최종 시각의 상세 경계
- 재신청 시 기존 출결 처리와 이력 보존 범위
- 블랙홀 판정식·확인 주기, 사용자 정보 삭제 범위·기존 FK 참조·주최 중인 활동과 소모임 처리, 재로그인 시 계정 생성 방지
- 기록 보존 기한·영구 파기 절차
- 활동 참가자 제거 정책
