## 축소 MVP — 2026-10-14 확정

| 구분 | 범위 |
| --- | --- |
| 유지 | 42 로그인·내 정보, 동아리 공개 조회와 기존 모집 응답 |
| 동아리 활동 | 활동 글·사진, 개최일·정원·현재 인원·모집 종료일, 본인 선착순 참가·취소 |
| 소모임 | 모집 글·기본 이미지, 개최일·정원·현재 인원·모집 종료일, 본인 선착순 참가·취소 |
| 공지 | 해당 동아리 ClubManager의 공지 작성·공개 조회 |
| 삭제 준비 | 활동·공지·소모임의 deleted_at과 미삭제 조회 조건; 삭제 버튼·API는 후속 |
| 추가 범위 합의 | 기존 부원 관리, 출결, 반복 모임·고정 멤버, 동아리 운영 기능의 추가 구현 |
| 제외 | 입부 모집 설정, 승인제, 개인 탈퇴, 블랙홀 처리, 활동보고·결제 |

활동 참가 모집과 동아리 입부 모집은 별개입니다. 참가로 ClubMember 가입 관계를 만들지 않습니다.
기존 users·clubs 스키마와 공개 조회 계약은 유지합니다. 기존 상세 확장 정책은 [후속 설계](future-design.md)에 보관하며 현재 MVP의 필수 작업으로 간주하지 않습니다.

## 로그인 및 인증 — 확정

- 42 OAuth 로그인만 제공하며, 42 사용자 조회 응답의 이메일 도메인이 정확히 `42gyeongsan.kr`인 계정만 허용합니다. 이메일 도메인은 대소문자를 구분하지 않으며 유사 접미사·다른 캠퍼스·누락된 이메일은 허용하지 않습니다. 이메일은 가입 자격 검사에만 사용하고 DB에 저장하지 않습니다.
- 최초 로그인은 42 고유 ID로 USER 계정을 생성합니다. 이후 로그인은 같은 ID의 이름·로그인명을 갱신하고 내부 ID·기존 서비스 역할·생성 시각을 보존합니다. 동시 최초 로그인도 계정 하나만 생성합니다.
- 로그인 상태는 서버 세션으로 유지하며 8시간 미사용 시 만료됩니다. 로그아웃은 세션을 무효화합니다. 세션에는 내부 사용자 ID와 서비스 역할만 보관하고 42 원본 프로필·42 API 토큰은 보관하지 않습니다.
- 매 요청 현재 DB 역할을 확인하여 ADMIN 부여·해제가 다음 요청에 반영되도록 합니다. 사용자 행이 없으면 기존 세션을 무효화합니다. 최초 ADMIN은 운영자가 DB에서 지정하며 본인 역할 변경 API는 두지 않습니다.
- 변경 요청에는 CSRF 토큰이 필요합니다. 로그인·로그아웃 뒤에는 현재 세션의 CSRF 토큰을 다시 조회합니다.
- 블랙홀 판정·계정 상태 전환·개인정보 제거·기존 세션 차단은 MVP에서 제외합니다. MVP 로그인·권한 검사는 블랙홀 상태를 고려하지 않으며 관련 계정 상태나 처리 작업을 추가하지 않습니다.

## 사용자 역할과 동아리 관리 권한

| 구분 | 표현 | 권한 범위 |
| --- | --- | --- |
| 일반 교육생 | User.role = USER | 공개 정보 조회, 로그인 후 소모임 생성·참여 신청 |
| 운영진 | User.role = ADMIN | 서비스 운영 권한; 운영 API·회원 관리의 추가 구현은 별도 합의 |
| 동아리 관리자(회장) | 해당 동아리의 ClubManager 관계 | 해당 동아리의 활동·공지 작성; 운영 기능은 후속 설계 |

공개 조회만 하는 방문자를 위해 계정을 생성할 필요는 없습니다.
회장은 해당 동아리의 ClubManager 관계를 가진 사용자로 표현하며 별도 회장 계정·테이블·전역 역할을 만들지 않습니다. USER와 ADMIN 모두 ClubManager가 될 수 있고 동아리 관리 권한은 동일합니다.
ADMIN이면서 ClubManager인 사용자는 운영진 권한과 해당 동아리 관리 권한을 함께 가집니다.
운영진도 해당 동아리의 ClubManager로 지정되어야 소개·모집 정보·활동·공지를 등록하거나 수정할 수 있습니다. 운영진 역할만으로 해당 권한을 부여하지 않습니다.
활동·소모임의 주최자와 동아리 관리자는 별개입니다. 출결 등 확장 기능의 권한은 [후속 설계](future-design.md)를 따릅니다.

### ClubManager 규칙 — 확정

- 한 사용자가 여러 동아리를 관리할 수 있습니다.
- 한 동아리에 여러 관리자를 허용합니다.
- 관리자가 없는 동아리의 생성과 유지를 허용합니다.
- 각 ClubManager는 반드시 사용자 한 명과 동아리 한 개에 연결됩니다.
- 동일한 사용자·동아리 조합을 중복 등록할 수 없습니다.
- ERD에는 필수 사용자·동아리 참조와 `(user_id, club_id)` 복합 유니크 제약조건을 반영합니다.
- 운영진이 관계를 생성하거나 제거하여 권한을 부여·해제합니다.
- 마지막 관리자의 권한도 해제할 수 있습니다. 동아리와 기존 활동·공지는 유지합니다.
- 관리자 부재만으로 운영 상태나 공개 여부를 자동 변경하지 않습니다.
- 현재 설계에서는 관리자 사이에 대표자·부관리자 등 별도 권한 등급을 두지 않습니다.

ClubManager는 권한을 기록하고, 서비스 로직은 로그인 사용자와 대상 동아리의 관계를 확인해 요청을 허용하거나 거부합니다.
전역적인 동아리 관리자 역할 하나만으로 리소스 접근을 허용하지 않습니다.

### 작성자와 수정 권한 — 현재 설계 방향

- Activity와 Notice의 작성자는 ClubManager가 아닌 User에 연결합니다.
- 작성자는 누가 등록했는지 기록하기 위한 정보입니다.
- 수정·삭제 권한은 작성자 여부보다 해당 동아리의 현재 관리 권한을 기준으로 검사합니다.
- 새 관리자는 기존 관리자가 작성한 활동·공지도 관리할 수 있습니다.
- 관리 권한 해제 후에도 기존 작성자 정보와 게시물을 유지합니다.

### 동아리 활동 주최자 — 확정

- 최초 작성자(author_id)와 지정 주최자(organizer_id)는 별도 User 관계이며 같은 사용자여도 됩니다.
- 동아리 관리자가 활동을 등록하고 주최자를 지정합니다. 서비스에 가입된 일반 User도 주최자가 될 수 있습니다.
- 활동 생성과 주최자의 참가 관계 생성은 같은 트랜잭션에서 처리합니다.
- 주최자 지정만으로 동아리 소개·다른 활동의 수정 권한을 얻지는 않습니다.
- 주최자 변경·명단 관리·출결은 [후속 설계](future-design.md#활동-주최자-변경--확정)의 권한과 기록 유지 정책을 참고합니다.

## 선착순 참가와 취소

| 상태 | 의미 | 허용 전이 |
| --- | --- | --- |
| CONFIRMED | 참가 확정, 정원에 포함 | 본인 취소 시 CANCELLED |
| CANCELLED | 참가 취소, 정원에서 제외 | 모집 조건을 충족해 재참가하면 CONFIRMED |

- 활동·소모임은 FIRST_COME만 사용합니다. 승인 대기·승인/거절·별도 대기열은 두지 않습니다.
- 로그인한 본인이 참가·취소합니다. 요청 본문의 임의 userId로 다른 사람을 참가시키지 않습니다.
- 마감·정원·중복 참가를 서버에서 검사하며 동시 요청에서도 정원을 초과하지 않아야 합니다.
- 주최자는 자동 참가하고 정원에 포함됩니다. 소모임은 회차 생성 시 주최자의 참가 관계를 함께 만듭니다. 주최자의 개별 참가 취소 예외는 기존 정책을 유지합니다.
- 취소는 물리 삭제가 아닌 상태 변경이며 재참가는 기존 관계를 재사용합니다. 이미 CONFIRMED인 관계의 중복 참가는 거부합니다.
- 같은 활동·사용자 또는 회차·사용자 조합에 하나의 관계만 둡니다. 주최자의 다른 사용자 수동 등록은 핵심 MVP에서 제외합니다.
- 소모임은 동아리와 독립적이며 로그인한 생성자가 주최자입니다. 주최자는 현재 범위에서 변경하지 않습니다.

## 일정과 표시

- 개최일과 모집 종료일은 별개입니다. D-Day는 Asia/Seoul의 오늘과 개최일 차이로 계산하며 당일은 D-Day, 개최일이 지난 뒤에는 종료로 표시합니다.
- 목록·상세에 전체 정원(capacity), CONFIRMED 현재 인원(currentParticipantCount), 잔여 정원과 모집 종료일을 제공합니다. D-Day와 인원 집계는 저장하지 않습니다.
- 소모임은 기존의 시작 최소 2시간 전 모집 공개 조건을 유지합니다. 즉시 공개는 현재 시각, 예약 공개는 예약 시각을 기준으로 하며 과거 공개 시각 입력으로 우회할 수 없습니다.
- 소모임 모집 마감은 시작 이전으로 설정합니다. 신규·재참가는 마감 전, 회차 참가 취소는 시작 전까지 허용하는 방향이며 상세 경계는 구현 전 확정합니다. 확정 인원보다 정원을 줄이지 않습니다.
- 일회성 소모임도 실제 회차 하나를 사용하는 기존 구조를 참고합니다. 반복·고정 멤버 확장은 별도 합의 대상입니다.
- 활동 사진 첨부는 포함합니다. 소모임 기본 이미지는 이미지가 없는 경우 사용하는 공통 표시 자산으로 별도 업로드를 필수로 요구하지 않습니다.
- 활동·공지는 등록 즉시 공개하며 임시저장을 두지 않습니다. 활동·공지·소모임의 일반 조회는 deleted_at이 있는 글을 제외합니다. 참가 취소와 글 삭제는 별개입니다.

## 기존 동아리 조회 정책

동아리 운영 상태는 ACTIVE / ARCHIVED이며 휴면 상태는 두지 않습니다. 일반 목록은 ACTIVE를 기본으로 조회하고 ARCHIVED 필터와 아카이브 상세 조회를 지원합니다.
예상 동아리 10개 미만·활성 사용자 200명 미만 규모에서는 이름·설명으로 안내하며 별도 분류 필드·필터를 두지 않습니다.
아래 모집 계산은 이미 구현된 공개 응답을 유지하기 위한 정책입니다. 입부 모집 설정 API는 현재 MVP에서 제외합니다.

### 모집 정보와 상태 — 확정

Club에 모집 계획 여부, 시작일, 종료일, 조기 마감 여부 및 지원 방법을 관리합니다.
지원은 외부 안내 경로로 진행하며, 서비스 내부 지원서 접수는 MVP에서 구현하지 않습니다.

표시용 모집 상태는 다음 순서로 계산합니다.

| 우선순위 | 조건 | 상태 |
| --- | --- | --- |
| 1 | 모집 계획 없음 | 모집 안 함 |
| 2 | 조기 마감 처리됨 | 마감 |
| 3 | 시작일 전 | 모집 예정 |
| 4 | 종료일이 있고 종료일이 지남 | 마감 |
| 5 | 위 조건에 해당하지 않음 | 모집 중 |

- 모집 계획이 있는 경우 시작일은 필수입니다.
- 종료일이 없으면 시작일부터 상시 모집합니다.
- 종료일은 시작일보다 빠를 수 없습니다. 같은 날 시작하고 종료할 수 있습니다.
- 한국 시간(`Asia/Seoul`) 기준으로 시작일 당일부터 종료일 당일까지 모집 중입니다.
- 일정 종료 전에도 수동으로 조기 마감할 수 있습니다.
- 표시용 모집 상태는 조회 시 계산하여 날짜와 상태가 불일치하지 않도록 합니다.
- 모집 회차별 이력은 MVP에서 관리하지 않습니다.

## 남은 결정 사항

| 구현 전에 정할 항목 | 결정할 내용 |
| --- | --- |
| 활동 일정 | 개최 시각 표현, 모집 종료일의 시각 경계, 참가 취소 최종 시점 |
| 활동 사진 | 저장·업로드 방식, 개수·크기·형식 제한, 실패·미사용 파일 정리 |
| 소모임 일정 | 신청·취소 가능 시각의 상세 경계, 핵심 MVP의 회차 생성 흐름 |
| 추가 기능 범위 | 운영 API·부원 관리·출결·반복 모임·고정 멤버의 포함 여부 |

HTTP DTO·페이지네이션은 [API 설계 항목](api-endpoints.md#구현-전-확정할-계약), 스키마·잠금 전략은 [ERD 설계 항목](erd.md#구현-전-확정할-사항)에서 관리합니다.
확장 기능만의 미정 정책은 [후속 설계](future-design.md#확장-시-결정할-사항)를 참고하며 MVP의 선행 조건으로 두지 않습니다.

## 추후 확장 기능 — MVP 제외

| 항목 | 참고 설계 |
