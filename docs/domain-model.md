## 축소 MVP — 2026-10-14 확정

| 구분 | 범위 |
| --- | --- |
| 유지 | 42 로그인·내 정보, 동아리 공개 조회와 기존 모집 응답 |
| 동아리 활동 | 활동 글·사진, 개최·모집 마감 일시·정원·현재 인원, 본인 선착순 참가·취소 |
| 소모임 | 모임·첫 회차 함께 생성, 같은 모임에 다음 회차 수동 추가, 예정·지난 회차 조회, 회차별 참가·취소·출결 |
| 공지 | 해당 동아리 ClubManager의 공지 작성·공개 조회 |
| 삭제 준비 | 활동·공지·소모임의 deleted_at과 미삭제 조회 조건; 삭제 버튼·API는 후속 |
| 권한 관리 | 초기 DB 등록, SUPER_ADMIN의 ADMIN·회장 권한 부여·회수 |
| 부원 관리 | ADMIN 직접 등록·재등록, 현재 부원 명단·가입 현황 조회 |
| 기본 출결 | 주최자의 미확인·출석 수동 기록, 참가자 본인 상태 조회 |
| 추가 범위 합의 | 반복 일정 자동 생성·고정 멤버, 동아리 운영 기능의 추가 구현 |
| 제외 | 글 수정·참가 후 일정 변경, 입부 모집 설정, 참가 승인제, 개인 탈퇴, 블랙홀 처리, 활동보고·결제 |

활동 참가 모집과 동아리 입부 모집은 별개입니다. 참가로 ClubMember 가입 관계를 만들지 않습니다.
기존 users·clubs 스키마와 공개 조회 계약은 유지합니다. 기존 상세 확장 정책은 [후속 설계](future-design.md)에 보관하며 현재 MVP의 필수 작업으로 간주하지 않습니다.

## 로그인 및 인증 — 확정

- 42 OAuth 로그인만 제공하며, 42 사용자 조회 응답의 이메일 도메인이 정확히 `student.42gyeongsan.kr`(교육생) 또는 `42gyeongsan.kr`(직원)인 계정을 허용합니다. 이메일 도메인은 대소문자를 구분하지 않으며 유사 접미사·다른 캠퍼스·누락된 이메일은 허용하지 않습니다. 이메일은 가입 자격 검사에만 사용하고 DB에 저장하지 않습니다.
- 최초 로그인은 교육생·직원 모두 42 고유 ID로 USER 계정을 생성합니다. 직원 이메일 도메인으로 ADMIN·SUPER_ADMIN 권한을 자동 부여하지 않습니다. 이후 로그인은 같은 ID의 이름·로그인명을 갱신하고 내부 ID·기존 서비스 역할·생성 시각을 보존합니다. 동시 최초 로그인도 계정 하나만 생성합니다.
- 로그인 상태는 서버 세션으로 유지하며 8시간 미사용 시 만료됩니다. 로그아웃은 세션을 무효화합니다. 세션에는 내부 사용자 ID와 서비스 역할만 보관하고 42 원본 프로필·42 API 토큰은 보관하지 않습니다.
- 매 요청 현재 DB 역할을 확인하여 ADMIN·SUPER_ADMIN 역할 변경이 다음 요청에 반영되도록 합니다. 사용자 행이 없으면 기존 세션을 무효화합니다. 초기 최고 관리자와 후속 권한 부여 방식은 아래 운영 초기화 정책을 따릅니다.
- 변경 요청에는 CSRF 토큰이 필요합니다. 로그인·로그아웃 뒤에는 현재 세션의 CSRF 토큰을 다시 조회합니다.
- 블랙홀 판정·계정 상태 전환·개인정보 제거·기존 세션 차단은 MVP에서 제외합니다. MVP 로그인·권한 검사는 블랙홀 상태를 고려하지 않으며 관련 계정 상태나 처리 작업을 추가하지 않습니다.

## 사용자 역할과 동아리 관리 권한

| 구분 | 표현 | 권한 범위 |
| --- | --- | --- |
| 일반 사용자(교육생·직원) | User.role = USER | 공개 정보 조회, 로그인 후 소모임 생성·참여 신청 |
| 운영진 | User.role = ADMIN | 부원 직접 등록·가입 현황 조회; 나머지 운영 API는 별도 합의 |
| 최고 관리자 | User.role = SUPER_ADMIN | ADMIN 및 동아리 회장 권한 부여·회수, ADMIN 운영 기능 포함; 회장·주최자·부원 조건은 우회하지 않음 |
| 동아리 관리자(회장) | 해당 동아리의 ClubManager 관계 | 해당 동아리의 활동·공지 작성; 운영 기능은 후속 설계 |

공개 조회만 하는 방문자를 위해 계정을 생성할 필요는 없습니다.
회장은 해당 동아리의 ClubManager 관계를 가진 사용자로 표현하며 별도 회장 계정·테이블·전역 역할을 만들지 않습니다. USER와 ADMIN 모두 ClubManager가 될 수 있고 동아리 관리 권한은 동일합니다.
ADMIN이면서 ClubManager인 사용자는 운영진 권한과 해당 동아리 관리 권한을 함께 가집니다.
운영진도 해당 동아리의 ClubManager로 지정되어야 소개·모집 정보·활동·공지를 등록하거나 수정할 수 있습니다. 운영진 역할만으로 해당 권한을 부여하지 않습니다.
동아리 활동의 주최자는 작성한 회장입니다. 소모임의 주최자는 생성자이며 동아리 관리 권한과 무관합니다. 출결은 해당 주최자가 관리합니다.

### 초기 등록과 최고 관리자 — 확정

- 초기 동아리·회장·최고 관리자 정보는 운영자가 전달받아 DB에 입력합니다. 동아리 생성 API는 MVP에 추가하지 않습니다.
- 최고 관리자는 별도 비밀번호 계정이 아니라 실제 42 사용자 계정에 SUPER_ADMIN을 지정하는 방식으로 설계합니다. 일반 OAuth 로그인은 계속 USER로만 신규 생성합니다.
- 이후 ADMIN 부여·회수와 ClubManager 관계 부여·회수는 최고 관리자만 수행합니다. ADMIN 회수는 USER로 변경하며 사용자 계정·부원 관계·게시물은 삭제하지 않습니다. 회장 권한 회수도 해당 관리 관계만 제거합니다.
- SUPER_ADMIN 생성·회수는 일반 권한 관리 API에 노출하지 않습니다. 초기 DB 지정으로 시작하며 최고 관리자 본인·타인을 ADMIN/USER로 변경하는 요청은 거절합니다.
- SUPER_ADMIN도 활동 작성에는 해당 동아리 회장 관계가 필요합니다. 다른 주최자의 참가자·출결 관리나 부원 관계 없는 명단 조회는 허용하지 않습니다. 최고 권한은 권한 부여·회수와 운영 관리에 적용하며 업무별 회장·주최자·부원 조건을 우회하지 않습니다.
- 현재 코드와 DB는 USER/ADMIN/SUPER_ADMIN을 지원합니다. V3에서 기존 V1을 변경하지 않고 역할 CHECK와 club_managers를 추가했습니다. 초기 입력은 [운영 절차와 SQL 틀](initial-data-setup.md)을 사용하며 사용자 검색·ADMIN·회장 권한 관리 API는 1단계에서 구현했습니다. 최고 관리자 대상 ADMIN 변경은 409로 거절합니다. 회장 관계 관리는 동아리 상태와 관계없이 가능하지만 작성 권한은 ACTIVE 동아리로 제한합니다.

### ClubManager 규칙 — 확정

- 한 사용자가 여러 동아리를 관리할 수 있습니다.
- 한 동아리에 여러 관리자를 허용합니다.
- 관리자가 없는 동아리의 생성과 유지를 허용합니다.
- 각 ClubManager는 반드시 사용자 한 명과 동아리 한 개에 연결됩니다.
- 동일한 사용자·동아리 조합을 중복 등록할 수 없습니다.
- ERD에는 필수 사용자·동아리 참조와 `(user_id, club_id)` 복합 유니크 제약조건을 반영합니다.
- 최고 관리자가 관계를 생성하거나 제거하여 권한을 부여·해제합니다.
- 마지막 관리자의 권한도 해제할 수 있습니다. 동아리와 기존 활동·공지는 유지합니다.
- 관리자 부재만으로 운영 상태나 공개 여부를 자동 변경하지 않습니다.
- 현재 설계에서는 관리자 사이에 대표자·부관리자 등 별도 권한 등급을 두지 않습니다.

ClubManager는 권한을 기록하고, 서비스 로직은 로그인 사용자와 대상 동아리의 관계를 확인해 요청을 허용하거나 거부합니다.
전역적인 동아리 관리자 역할 하나만으로 리소스 접근을 허용하지 않습니다.

### 작성자와 후속 수정 권한

- 글 수정은 MVP에서 제외하며 아래 수정·삭제 권한은 후속 기능을 위한 설계입니다.
- Activity와 Notice의 작성자는 ClubManager가 아닌 User에 연결합니다.
- 작성자는 누가 등록했는지 기록하기 위한 정보입니다.
- 수정·삭제 권한은 작성자 여부보다 해당 동아리의 현재 관리 권한을 기준으로 검사합니다.
- 새 관리자는 기존 관리자가 작성한 활동·공지도 관리할 수 있습니다.
- 관리 권한 해제 후에도 기존 작성자 정보와 게시물을 유지합니다.

### 동아리 활동 주최자 — 확정

- ACTIVE 동아리의 회장(ClubManager)만 활동을 작성할 수 있습니다. 작성한 회장이 곧 주최자이며 author_id와 organizer_id는 같은 사용자입니다.
- 두 식별자는 서버가 인증 사용자로 설정합니다. 클라이언트에서 주최자 ID를 받거나 다른 사용자를 지정하는 기능·후보 검색 API는 MVP에 두지 않습니다.
- 활동 생성과 주최자의 참가 관계 생성은 같은 트랜잭션에서 처리합니다.
- 주최자 지정만으로 동아리 소개·다른 활동의 수정 권한을 얻지는 않습니다.
- 주최자는 참가 명단과 [기본 출결](#기본-출결--확정)을 관리합니다. 주최자 변경은 [후속 설계](future-design.md#활동-주최자-변경--확정)를 따릅니다.

## 동아리 가입 한도 — 확정

- 사용자당 활성 동아리의 동시 가입은 정책상 최대 2개입니다. 부원 직접 등록은 ADMIN 권한을 가진 운영자가 담당하며 이 한도를 확인하고 등록 여부를 판단합니다.
- 가입 관계는 ClubManager 관리 권한과 별도로 관리합니다. 관리 권한 부여만으로 회원 가입을 자동 생성하거나 가입 수를 증가시키지 않습니다.
- 등록 화면에서 대상 사용자의 현재 가입이 확정된 동아리 목록과 개수를 등록 대상 옆에 표시합니다. 동아리 이름·ID를 제공하여 운영자가 기존 가입 관계를 확인할 수 있도록 합니다.
- 가입 동아리 수에 따른 자동 거절이나 등록 시 자동 한도 검사를 두지 않습니다. 시스템의 강제 차단 대신 운영자가 표시된 가입 내역으로 확인하는 방식입니다. ADMIN 등록 권한 검증은 별도로 적용합니다.
- 동아리 관리자(ClubManager)는 관리 권한만으로 부원을 등록할 수 없습니다. ADMIN 권한도 가진 경우에는 운영자 자격으로 등록할 수 있습니다.
- ADMIN 운영자가 기존 부원을 직접 등록합니다. 사이트 내부 동아리 가입 신청·승인 대기·거절 기능은 두지 않습니다.
- 후속 아카이브 실행 기능을 도입하면 기존 ACTIVE 가입 관계를 모두 LEFT로 전환하므로 최대 2개 가입 한도에서 제외됩니다. 가입 관계 자체는 보존하며 구체적인 전환 규칙은 [아카이브 정책](future-design.md#게시-및-아카이브-정책--확정)을 따릅니다. 한도에는 ClubMember.status = ACTIVE이면서 Club.operationStatus = ACTIVE인 관계만 포함합니다.
- 아카이브 상태에서는 ADMIN도 신규 가입·재가입을 등록할 수 없습니다. 재활성화 후 ADMIN이 가입·재가입을 등록해야 합니다.
- 본인 탈퇴와 블랙홀 이후 가입 관계 처리는 MVP에서 제외하고 추후 확장으로 둡니다.

### 동아리 가입 관계 — 확정

- ClubMember는 사용자와 동아리 사이의 가입 관계이며 ACTIVE(가입 중)와 LEFT(탈퇴) 두 상태를 사용합니다. 동아리 자체의 운영 상태와 구분합니다.
- ADMIN 운영자의 최초 가입 등록으로 ACTIVE 관계를 생성하고 등록 운영자·가입 시각을 기록합니다. 회원 등록이 관리자 권한을 부여하지는 않습니다.
- LEFT 전환은 후속 아카이브 일괄 처리에 사용합니다. 현재 MVP에 아카이브 실행 API를 추가하지 않습니다. 본인 탈퇴 신청·승인·개별 탈퇴 처리 API는 제공하지 않습니다.
- 재가입은 ADMIN 운영자의 직접 등록으로 기존 LEFT 관계를 ACTIVE로 변경하고 등록 운영자·가입 시각을 갱신하며 탈퇴 시각을 비웁니다.
- 동일한 사용자·동아리 조합에는 관계 하나만 유지하여 중복 가입을 방지합니다.
- 등록 화면에는 ACTIVE인 가입 관계의 동아리 목록과 각 동아리의 운영 상태를 표시하며, 한도에 포함되는 활성 동아리 가입 수를 제공합니다. 아카이브로 LEFT가 된 관계를 포함하여 모든 LEFT 관계는 현재 가입 목록과 한도에서 제외합니다. 가입 관계는 물리 삭제하지 않고 최초 관계 생성 시각과 최신 가입 상태를 보존합니다. 재가입 시 이전 가입 시각·등록 운영자는 갱신되고 탈퇴 시각은 비워지므로, 반복 가입·탈퇴의 전체 이력은 보존하지 않습니다.

### 동아리 회원 명단 조회 — 확정

- 해당 동아리의 ACTIVE 가입 관계를 가진 회원은 현재 회원 명단을 조회할 수 있습니다. 명단에는 해당 동아리의 ACTIVE 회원만 포함합니다.
- 비회원과 LEFT 상태의 탈퇴 회원에게 명단을 공개하지 않습니다. ADMIN 역할이나 ClubManager 권한만으로 회원 명단 조회 권한을 자동 부여하지 않습니다.
- 후속 아카이브 실행 기능을 도입하면 모든 ACTIVE 가입 관계가 LEFT로 전환되므로 기존 회원도 회원 자격으로 명단을 조회할 수 없습니다. 가입 관계의 DB 보존과 명단 조회 권한은 구분합니다. 현재 MVP에는 아카이브 실행 API가 없습니다.
- 가입 등록 화면에서 ADMIN이 조회하는 사용자의 현재 가입 동아리 정보는 별도의 운영 기능으로 유지합니다.

## 소모임과 개최 회차 — 확정

- 동아리는 부원·관리 권한을 가진 조직이고, 소모임은 주최자가 회차를 열어 참가자를 모집하는 단위입니다. 소모임도 기존 User를 주최자·회차 참가자로 참조하지만 고정 부원 관계는 두지 않습니다.
- 일회성 소모임은 모임과 첫 회차 하나를 생성합니다. 정기 소모임은 같은 gathering ID 아래 주최자가 다음 회차를 직접 추가합니다. 요일·주기를 등록해 자동으로 회차를 생성하는 기능은 후속 확장입니다.
- 모임에는 소개·주최자·기본 이미지를 두고, 회차에는 개최·종료·모집 마감 일시·장소·정원·참가자·출결을 둡니다. 각 회차의 참가·마감·출결은 독립적으로 관리합니다.
- 최초 작성은 모임·첫 회차·주최자 참가 관계를, 다음 회차 추가는 새 회차·주최자 참가 관계를 각각 같은 트랜잭션에서 생성합니다. 다음 회차의 일시·장소·정원·모집 마감은 새로 입력받습니다.
- 참가자는 원하는 회차마다 신청합니다. 이전 회차 참가자를 다음 회차에 자동 등록하지 않으며 기존 참가·출결 기록을 새 회차에 복사하지 않습니다.
- 소모임 상세는 소개와 예정·지난 회차를 보여주고 참가 버튼은 해당 회차에 연결합니다. 일회성은 회차 하나의 일정·참가 기능을 바로 보여줄 수 있습니다. 회차 조회는 소속 모임이 일치하는지 검사합니다.
- 다음 회차 추가는 새 일정 생성입니다. 이미 만든 글·회차를 수정하는 기능은 계속 MVP에서 제외합니다. 주최자 변경·고정 멤버 가입·자동 반복도 후속 범위입니다.

## 선착순 참가와 취소

| 상태 | 의미 | 허용 전이 |
| --- | --- | --- |
| CONFIRMED | 참가 확정, 정원에 포함 | 본인 취소 시 CANCELLED |
| CANCELLED | 참가 취소, 정원에서 제외 | 모집 조건을 충족해 재참가하면 CONFIRMED |

- 활동·소모임은 FIRST_COME만 사용합니다. 승인 대기·승인/거절·별도 대기열은 두지 않습니다.
- 로그인한 본인이 참가·취소합니다. 요청 본문의 임의 userId로 다른 사람을 참가시키지 않습니다.
- 마감·정원·중복 참가를 서버에서 검사하며 동시 요청에서도 정원을 초과하지 않아야 합니다.
- 주최자는 자동 참가하고 정원에 포함됩니다. 소모임은 회차 생성 시 주최자의 참가 관계를 함께 만듭니다. 주최자의 개별 참가 취소 예외는 기존 정책을 유지합니다.
- 취소는 물리 삭제가 아닌 상태 변경이며 재참가는 기존 관계를 재사용합니다. 이미 CONFIRMED인 관계의 중복 참가는 거부합니다.
- 같은 활동·사용자 또는 회차·사용자 조합에 하나의 관계만 둡니다. 주최자의 다른 사용자 수동 등록은 핵심 MVP에서 제외합니다.
- 소모임은 동아리와 독립적이며 로그인한 생성자가 주최자입니다. 주최자는 현재 범위에서 변경하지 않습니다.

## 일정과 표시

- 활동·소모임의 개최와 모집 마감은 날짜·시각을 필수로 입력받습니다. 모집 마감은 개최 시각보다 이전이어야 합니다.
- 신규 참가·재참가·본인 취소는 모두 서버 시각이 모집 마감 전이면서 개최 전일 때만 허용합니다. 정확히 마감 시각에 도달하면 참가·취소 모두 불가합니다. 개최 전이라도 모집 마감 후에는 취소할 수 없습니다.
- 소모임 회차는 생성 즉시 모집을 공개합니다. 서버가 정한 생성 시각에서 시작까지 최소 2시간이 남아 있어야 하며, 클라이언트가 공개 시각을 지정할 수 없습니다. 예약 공개는 [후속 설계](future-design.md#모집-공개와-일정)입니다.
- 소모임의 첫 회차·다음 회차 생성은 [회차 정책](#소모임과-개최-회차--확정)을 따릅니다. 모든 새 회차에 동일한 모집 공개·마감·참가·취소 조건을 적용합니다.
- 활동·공지·소모임의 글 수정과 개최 일시·장소·정원·모집 마감 변경은 MVP에서 제공하지 않습니다. 참가 후 일정 변경도 확장 시 설계합니다. 참가 상태·출결 기록은 글 수정과 별개의 MVP 기능입니다.
- 개최일과 모집 마감일은 별개입니다. D-Day는 Asia/Seoul의 오늘과 개최일 차이로 계산하며 당일은 D-Day, 개최일이 지난 뒤에는 종료로 표시합니다.
- 목록·상세에 전체 정원(capacity), CONFIRMED 현재 인원(currentParticipantCount), 잔여 정원, 개최·모집 마감 일시를 제공합니다. D-Day와 인원 집계는 저장하지 않습니다.
- 활동·소모임 목록은 모집 중인 항목을 우선하고 각 그룹에서 개최 시각 오름차순, 같은 시각이면 ID 오름차순으로 정렬합니다. 모집 중은 공개되어 있고 마감·개최 전이며 잔여 정원이 있는 미취소 항목입니다. 마감·종료된 글은 뒤쪽에 계속 표시하며 검색은 후속 확장입니다. 기존 Club 목록의 ID 정렬은 유지합니다.
- 활동 사진은 [선택 첨부 정책](#활동-사진--확정)을 따릅니다. 소모임 기본 이미지는 이미지가 없는 경우 사용하는 공통 표시 자산으로 별도 업로드를 필수로 요구하지 않습니다.
- 활동·공지는 등록 즉시 공개하며 임시저장을 두지 않습니다. 활동·공지·소모임의 일반 조회는 deleted_at이 있는 글을 제외합니다. 참가 취소와 글 삭제는 별개입니다.

## 활동 사진 — 확정

- 사진은 선택 첨부이며 0~5장을 허용합니다. 사진 없이도 활동을 등록할 수 있습니다.
- 첨부 순서를 유지하며 첫 번째 사진을 목록의 대표 이미지로 사용합니다. 사진이 없으면 프론트엔드가 공통 기본 이미지를 표시합니다. 기본 이미지는 실제 첨부 사진으로 저장하지 않습니다.
- 파일당 최대 5MB(5,242,880바이트), JPEG·PNG·WebP를 허용합니다. 백엔드는 확장자·요청 Content-Type만 신뢰하지 않고 실제 이미지 형식과 디코딩 가능 여부를 검증합니다.
- 활동 정보와 사진을 하나의 multipart 요청으로 백엔드에 전송하고, 백엔드가 검증 후 S3 같은 별도 파일 저장소에 업로드합니다. 별도 업로드 API와 브라우저 직접 업로드는 MVP에 도입하지 않습니다.
- DB에는 파일 본문이나 전체 조회 URL 대신 저장소 식별자(`storage_key`)와 표시 순서를 저장합니다. 백엔드는 활동 조회 시 저장소 식별자로 프론트엔드에서 사진을 표시할 수 있는 이미지 URL을 제공하며, 프론트엔드는 이 URL로 사진을 조회합니다. 파일명은 서버가 생성하며 사용자가 보낸 파일명으로 저장 경로를 결정하지 않습니다.
- 첨부 파일 하나라도 검증·업로드에 실패하면 활동 등록 전체를 실패 처리합니다. 업로드 또는 DB 저장 실패 시 해당 요청으로 저장한 파일을 정리하며, 정리 실패는 재시도할 수 있도록 기록합니다. 파일 저장소와 DB가 하나의 트랜잭션으로 묶인다고 가정하지 않습니다.
- 저장소는 S3를 사용하고 설정된 이미지 도메인 또는 15분 만료 서명 GET URL로 조회합니다. 정리 대기 파일 키를 업로드 전에 DB에 기록하고, 활동 저장과 함께 저널을 제거합니다. 실패 요청은 즉시 정리하고 남은 키는 10분 후부터 주기적으로 재시도합니다. 설정과 운영 조건은 [환경변수](environment-variables.md#활동-사진-저장소)를 따릅니다. 프론트엔드 기본 이미지 자산은 프론트 연동에서 확인합니다.

## 기본 출결 — 확정

| 상태 | 의미 |
| --- | --- |
| UNCHECKED | 미확인, 기본값 |
| PRESENT | 출석 |

- 활동·소모임의 CONFIRMED 참가자만 대상으로 하며 주최자도 포함합니다. 미확인을 결석으로 간주하거나 자동으로 출석 처리하지 않습니다.
- 현재 지정된 주최자가 명단에서 출석을 수동 기록하고 미확인으로 되돌릴 수 있습니다. ClubManager·ADMIN 역할만으로 출결 권한을 얻지 않습니다. 주최자 본인의 출결도 기록할 수 있습니다.
- 마지막 체크 사용자·시각만 기록하며 미확인으로 되돌리면 두 값도 비웁니다. 별도 변경 이력은 두지 않습니다.
- 참가자는 본인 출결을 조회하고 주최자는 참가자·출결 명단을 조회합니다. 공개 응답에는 명단·출결을 포함하지 않습니다.
- 취소·삭제된 활동 또는 회차의 출결 변경은 차단합니다. 출결 입력에 시작 시각 제한은 추가하지 않습니다.
- 출결이 있는 회차 관계의 재참가를 차단하는 기존 정책은 유지하며 기존 출결을 덮어쓰지 않습니다.
- 결석·지각·자동 판정·통계·이력·입력 시각 제한은 후속 확장입니다.

## 기존 동아리 조회 정책

동아리 운영 상태는 ACTIVE / ARCHIVED이며 휴면 상태는 두지 않습니다. 일반 목록은 ACTIVE를 기본으로 조회하고 ARCHIVED 필터와 아카이브 상세 조회를 지원합니다.
예상 동아리 10개 미만·활성 사용자 200명 미만 규모에서는 이름·설명으로 안내하며 별도 분류 필드·필터를 두지 않습니다.
아래 모집 계산은 이미 구현된 공개 응답을 유지하기 위한 정책입니다. 입부 모집 설정 API는 현재 MVP에서 제외합니다.

### 모집 정보와 상태 — 확정

Club에 모집 계획 여부, 시작일, 종료일, 조기 마감 여부 및 지원 방법을 관리합니다.
지원은 외부 안내 경로로 진행하며, 서비스 내부 지원서 접수는 MVP에서 구현하지 않습니다.

표시용 모집 상태는 다음 순서로 계산합니다.

| 우선순위 | 조건 | 상태 |
| --- | --- | --- |
| 1 | 모집 계획 없음 | 모집 안 함 |
| 2 | 조기 마감 처리됨 | 마감 |
| 3 | 시작일 전 | 모집 예정 |
| 4 | 종료일이 있고 종료일이 지남 | 마감 |
| 5 | 위 조건에 해당하지 않음 | 모집 중 |

- 모집 계획이 있는 경우 시작일은 필수입니다.
- 종료일이 없으면 시작일부터 상시 모집합니다.
- 종료일은 시작일보다 빠를 수 없습니다. 같은 날 시작하고 종료할 수 있습니다.
- 한국 시간(`Asia/Seoul`) 기준으로 시작일 당일부터 종료일 당일까지 모집 중입니다.
- 일정 종료 전에도 수동으로 조기 마감할 수 있습니다.
- 표시용 모집 상태는 조회 시 계산하여 날짜와 상태가 불일치하지 않도록 합니다.
- 모집 회차별 이력은 MVP에서 관리하지 않습니다.

## 남은 결정 사항

| 구현 전에 정할 항목 | 결정할 내용 |
| --- | --- |
| 배포·프론트 연동 | S3 버킷·실행 자격증명·이미지 도메인 설정과 프론트 기본 이미지 자산 확인 |
| 회차 표시 | 대표 회차·진행 중 분류는 아래 구현 세부 계약으로 확정; 실제 프론트 표시 연동 확인 |
| 추가 기능 범위 | 개최 취소·내 참가 목록·반복 일정 자동 생성·고정 멤버의 포함 여부 |

HTTP DTO·페이지네이션은 [API 계약](api-endpoints.md#dto와-프론트-연동-계약), 스키마·잠금 전략은 [ERD 설계 항목](erd.md#구현된-잠금정리-정책)에서 관리합니다.
확장 기능만의 미정 정책은 [후속 설계](future-design.md#확장-시-결정할-사항)를 참고하며 MVP의 선행 조건으로 두지 않습니다.

## 팀 합의 대기 — 보류

기록 보존 기간과 영구 파기 절차는 팀원 합의 후 확정합니다. 보류 중에는 기간 기반 자동 삭제를 도입하지 않습니다.

### MVP 구현 세부 계약

부원 ACTIVE 반복 등록은 최초 등록 정보를 보존합니다. 공지 제목은 최대 200자, 본문은 최대 50,000자이며 공백만 있는 값은 허용하지 않습니다.

활동 제목·본문 제한은 공지와 같고 개최와 모집 마감은 생성 시각 이후여야 합니다. 소모임도 제목·본문 제한을 동일하게 적용합니다. 소모임 회차는 즉시 모집 공개하며 개최는 생성 시각에서 최소 2시간 이후, 종료는 개최 이후, 모집 마감은 공개 이후·개최 이전입니다. 예약 공개 입력은 제공하지 않습니다.
소모임 대표 회차는 진행 중인 회차(가장 이른 시작) → 가장 가까운 예정 회차 → 가장 최근 지난 회차 순으로 선택합니다. 목록은 이 대표 회차를 기준으로 모집 중 우선·시작 시각·모임 ID 오름차순으로 정렬합니다. 회차 목록은 UPCOMING(시작 전, 시작 오름차순), ONGOING(시작 이상·종료 미만, 시작 오름차순), PAST(종료 이상, 시작 내림차순) 필터를 제공하며 필터가 없으면 전체 시작 오름차순입니다. 소모임 기본 이미지는 프론트 공통 자산이며 API는 null을 반환합니다.
주최자의 본인 취소는 거절하고 PRESENT인 참가자는 본인 취소도 거절합니다. 따라서 출결이 있는 취소 관계를 새로 만들지 않으며 기존 데이터에 PRESENT인 CANCELLED 관계가 있더라도 재참가는 거절합니다.
