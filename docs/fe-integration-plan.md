# 프론트엔드 요구사항 검토와 백엔드 구현 계획

작성일: 2026-10-17. 상태: 1단계 API·로그인 연동 검증 완료. 2단계는 정책 검토와 채택 항목의 BE 구현·HTTP 검증 완료, FE 화면은 미연결. 공개 연락처는 미제공 확정. 3단계는 ADMIN 통합 정책 검토·BE 구현·HTTP 검증 완료이며 FE 수정은 요청 범위에서 제외. 4단계는 소모임 전용 공지(EXT-01) 미도입 확정, EXT-02 참가 자격 정책·BE 구현·HTTP 검증 완료이며 동아리 기본정보(EXT-04-A) BE 검증 완료, 공지 삭제(EXT-05)는 DELETE-01~03 합의를 마쳐 구현 가능하며 나머지 후보는 미정.

## 목적과 기준

프론트엔드 요청과 현재 백엔드 구현을 대조하고, 확정 가능한 작업과 결정이 필요한 작업을 구분한다. 이 문서는 구현 순서와 미정 사항을 관리하며 업무 정책이나 HTTP 계약을 새로 확정하지 않는다. 전체 사용자 결정과 다음 실행 순서는 [의사결정 기록](decision-register.md)에 모은다.

검토한 FE 자료는 `42-clubs-FE` 저장소의 다음 문서다. 별도 저장소이므로 경로로 출처를 기록한다.

- `docs/BE_REQUIREMENTS.md`: 동아리 상세 정보·권한 검토 요청
- `docs/FE_BE_API_GAP.md`: 2026-10-17 기준 API 대조 결과
- `docs/FEATURE_BACKLOG.md`: 개선·보류 기능과 재검토 조건
- 실행 설정 참고: `docs/CLUB_API_PREVIEW.md`

FE 대조 문서가 참조한 BE 커밋과 검토 당시 BE HEAD는 `3741e81`이다. FE 문서는 로컬 작업본을 읽었으며, 문서에 기재된 FE 기준은 main `93c84ff` 기반이다. 실제 구현 착수 시 양쪽 변경분을 다시 확인한다. FE의 ‘맞음’은 명세와 코드의 대응을 뜻하며 실제 서버 연동 성공이나 운영 정책 확정을 뜻하지 않는다.

BE 기준은 [문서 관리 규칙](../README.md#문서-관리-ssot)에 따라 [도메인](domain-model.md), [ERD](erd.md), [API 명세](api-endpoints.md), 실제 코드와 테스트를 대조한다. [후속 설계](future-design.md)의 ‘확정’도 현재 구현 범위에 자동 편입하지 않는다.

## 미정 사항 처리 규칙

- 애매하거나 출처 간 내용이 충돌하면 기능 구현보다 기록을 먼저 한다. 해당 항목에 의존하지 않는 작업은 진행할 수 있다.
- 미정 항목의 결정 결과는 아래 표에서 빈칸으로 유지한다. 빈칸은 승인·기본값·기능 불필요를 뜻하지 않는다.
- 결정 전에는 추측한 DTO 필드·DB 컬럼·권한·임시 API·가짜 집계값을 추가하지 않는다. 필드명과 null/빈 배열의 의미도 계약 결정 대상이다.
- FE의 미제공 정보 `—` 표시를 유지한다. 미제공 정보와 실제 집계 결과 0을 구분한다.
- 결정되면 결정 결과·근거·일자를 기록하고 기준 문서를 먼저 갱신한다. 이후 상태를 `구현 가능`으로 바꾼다. 구현과 검증 증거가 있어야 `검증 완료`로 바꾼다.
- 상태는 `미정 → 구현 가능 → 구현 중 → 검증 완료`로 관리한다. 도입을 미룬 항목은 근거·재검토 조건과 함께 `보류`로 기록한다. 기능이 불필요하다고 합의한 항목은 `미도입 확정`으로 기록하고 별도 변경 요청 전까지 구현 대상에서 제외한다.

## 완료 판정 원칙

- 아래 체크리스트는 앞으로 충족해야 할 조건이며, 현재 충족했다는 뜻이 아니다.
- `검토 완료`는 구현 또는 보류에 필요한 결정과 근거를 기록한 상태다. `구현 완료`는 채택한 범위의 코드·문서·검증이 모두 끝나 항목 상태가 `검증 완료`인 경우다. 두 판정을 구분해 진행 기록에 남긴다.
- 검증 결과에는 대상 FE/BE 리비전·관련 미커밋 변경 유무, 실행 환경, 시나리오/입력 조건, 기대 결과·실제 결과, 증거 위치를 기록한다. 비밀값·세션 토큰은 남기지 않는다.
- 미실행·실패·정책 미정은 통과로 계산하지 않는다. 보류는 완료가 아니며, 사유·재검토 조건과 남은 영향을 기록한다.
- 단계 내 일부 항목만 완료되면 해당 ID와 완료 범위만 표시한다. 범위를 바꿀 때는 제외 항목과 근거를 명시하며, 의존하지 않는 다음 단계 작업은 진행할 수 있다.

## 1단계: 기존 API 연동 검증

새로운 업무 정책이 필요하지 않은 기존 계약 검증부터 진행한다. 실제 오류가 확인되면 기존 계약에 따른 수정인지 정책 변경인지 먼저 구분한다.

| 대상 | 확인 내용 | 완료 증거 |
| --- | --- | --- |
| 동아리·공지·활동·소모임 조회 | 중첩 경로, 공개 범위, 목록/상세 응답, 페이지네이션 | 요청 조건·응답·관련 테스트 결과 |
| 달력·마이페이지 | 전체 페이지 처리, 한국 날짜 경계, 활동/회차 구분, 본인 참가 내역 | FE 연동 시나리오 결과 |
| 글·활동·회차 생성 | 필수값, 첫 회차/다음 회차, 사진 multipart와 조회 URL | 생성 후 조회 결과 |
| 참가·취소 | 마감 경계, 중복·재참가, 정원 동시성, 주최자 제한, 출결 기록 제한 | 관련 통합 테스트 결과 |
| 회원·권한·출결 | 비회원 명단 접근 거절, 주최자 조건, 권한 관리 범위 | 허용·거절 역할별 테스트 결과 |
| 세션·CSRF | 로그인/로그아웃 후 토큰, 세션 쿠키, 인증 실패 응답 | 기존 테스트 및 실행 환경 확인 |

현재 API로 달력 구현이 가능하므로 달력 전용 API는 추가 작업에 넣지 않는다. FE의 모든 화면 로그인 요구만으로 BE 공개 조회를 인증 필수로 변경하지 않는다.

실제 42 로그인은 FE 자료에 따라 후순위로 검증한다. 실행 환경의 `AUTH_SUCCESS_URL`은 FE 해시 라우터의 `/#/auth/callback` 및 실제 포트와 맞추고 `AUTH_ALLOWED_ORIGINS`도 함께 확인한다. 예시는 `http://localhost:5176/#/auth/callback`이며 고정 운영 주소로 간주하지 않는다. 환경변수 변경 시 [환경변수 문서](environment-variables.md)와 `.env.example`을 함께 갱신한다.

### 1단계 완료 조건

- [x] 위 표의 모든 대상에 대해 기존 API 계약에 따른 정상·거절·경계 시나리오와 기대 응답을 정리했다.
- [x] 조회·생성·사진·참가·취소·회원·출결·마이페이지의 FE 요청이 실제 BE 응답과 연결되는 것을 확인했다. 목업 성공을 실제 연동 성공으로 계산하지 않았다.
- [x] 정원 동시성·마감 경계·중복 참가와 역할/관계별 접근 제한이 관련 테스트에서 통과했다. 기존 테스트가 충분하면 중복 테스트를 추가하지 않았다.
- [x] 발견한 계약 불일치를 수정하고 재검증했거나, 정책 결정이 필요한 항목으로 분리해 영향과 미완료 범위를 기록했다. 미해결 항목이 있으면 단계 전체 완료로 표시하지 않았다.
- [x] 실제 42 인증 후 FE 홈으로 복귀하고 로그인 상태가 유지되는 것을 확인했다. 사용자 브라우저 확인 결과를 자동 테스트와 구분해 기록했다.
- [x] 실제 로그인 상태에서 새로고침 후 인증 조회가 유지되는 것을 확인했다.
- [x] 실제 로그인한 브라우저의 로그아웃(CSRF 변경 요청) 후 새로고침해 인증이 해제되는 것을 확인했다. 별도 익명 세션의 프록시 CSRF 갱신/이전 토큰 거절 검증과 구분한다.
- [x] 코드 수정이 있었다면 `./gradlew build`가 통과했고, 실제 연동 결과와 별도로 기록했다.

실행 결과와 재실행 방법은 [1단계 검증 기록](fe-integration-stage1-verification.md)을 따른다. FE API 함수의 실제 HTTP 요청, 실행 중인 FE 프록시·BE의 익명 세션/CSRF/CORS, 사용자 브라우저의 실제 42 로그인·홈 복귀·새로고침·로그아웃을 확인했다. 2026-10-17 사용자 지시에 따라 이 API·로그인 연동 검증 범위의 1단계를 완료로 정리하고 2단계에 착수한다. 전체 업무 화면·제출 환경의 브라우저 확인은 후속 점검으로 유지하며 통과로 간주하지 않는다. 현 검증 범위에서 계약 불일치는 발견하지 못했다.

## 2단계: 동아리 상세 응답 검토

기존 `GET /api/v1/clubs/{clubId}` 보강을 우선 검토한다. 권장 검토 순서는 회원 수 → 회장 정보 → 공개 연락처 → 최근 참여이며, 각 항목의 결정이 끝나면 독립적으로 착수한다. 아래 구현 방향은 후보이며 확정 계약이 아니다.

현재 코드·FE 화면과의 대조, 항목별 구체적인 결정안과 구현 영향은 [2단계 검토 기록](fe-integration-stage2-review.md)에 남긴다.

| ID | 요청·출처 | 현재 상태와 결정할 질문 | 결정 후 구현 후보 | 상태 | 결정 결과·근거·일자 |
| --- | --- | --- | --- | --- | --- |
| DETAIL-01 | 회원 수 / BE_REQUIREMENTS | memberCount에 ACTIVE 부원과 현재 회장의 고유 사용자 수 반환. 겸직은 1명, 부원 관계 없는 회장도 포함. 아카이브도 같은 기준 | DB 합집합 집계. 가입 관계·명단 조회 권한은 변경하지 않음 | 구현 중 | 2026-10-17 사용자 회장 포함 승인. BE 구현·166개 테스트·FE 함수 HTTP 확인 완료. FE 화면 표시 미연결 |
| DETAIL-02 | 회장 정보 / BE_REQUIREMENTS | 공개 상세에 managers 배열, intraLogin·displayName만 반환. 복수 회장 지원, 없으면 [] | 공개용 DTO로 변환하고 지정·회수·표시 정보 갱신 반영. 권한 관리 API 변경 없음 | 구현 중 | 2026-10-17 사용자 승인. BE 구현·전체 테스트·FE 함수 HTTP 확인 완료. FE 화면 표시 미연결이므로 항목 전체 검증 완료와 구분 |
| DETAIL-03 | 공개 연락처 / BE_REQUIREMENTS | 공개 연락처 미제공으로 확정 | 저장 컬럼·조회 필드·입력 API 추가 대상에서 제외. 재도입 요청 시 검토 | 미도입 확정 | 2026-10-17 사용자 미제공 결정. 정책 미정이나 구현 누락과 구분 |
| DETAIL-04 | 최근 활동 / BE_REQUIREMENTS | 최근 시작한 미삭제 동아리 활동 1개. 제목·개최 시각·신청 확정/출석 확인 인원. 주최자 포함, 개인 명단 제외 | 상세 recentActivity 요약과 활동 목록·상세 presentParticipantCount. 대상 없으면 null | 구현 중 | 2026-10-17 사용자 합의. BE 169개 테스트·HTTP 10개 묶음/141건 통과. FE 화면 미연결 |

최근 참여 검토 시 추가로 주의할 점:

- CONFIRMED는 참가 신청 확정이며 실제 참석을 뜻하지 않는다. UNCHECKED는 결석이나 활동 부족으로 해석하지 않는다.
- 현재 출결은 개최 전에도 기록할 수 있으므로 최근 활동은 startsAt <= 서버 현재 시각 조건으로 미래 활동을 제외한다. 일반 활동 목록·상세의 출석 확인 인원은 해당 활동의 현재 기록을 그대로 집계한다.
- 최근 참여를 [후속 설계의 90일 활동도](future-design.md#활동도-계산), 평가 점수나 활동 등급으로 대체하지 않는다.
- 집계 구현 시 기능별 조회 서비스 경계를 지키고, 공개 요청에서 회원/참가자 명단 전체를 불러와 가공하는 방식은 피한다. 실제 성능에 따라 쿼리·인덱스를 검토하며 미리 스키마를 확장하지 않는다.

## 구현·검증·문서 반영 절차

1. 해당 ID의 질문에 대한 결정을 기록하고 영향 범위를 확인한다. 미정 질문이 구현에 영향을 주면 착수하지 않는다.

5. 코드 변경은 `./gradlew build`로 검증하고 FE 요청·응답을 확인한다. 문서만 변경하면 링크와 기준 문서의 일관성을 확인한다.
6. 기능 ID별 구현 파일·검증 명령과 결과·FE 연동 결과·커밋을 기록한다. 테스트 통과와 실제 연동 확인은 별도로 구분한다.
