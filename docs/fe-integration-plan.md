# 프론트엔드 요구사항 검토와 백엔드 구현 계획

작성일: 2026-10-17. 상태: 계획 작성, 기능 구현 미착수.

## 목적과 기준

프론트엔드 요청과 현재 백엔드 구현을 대조하고, 확정 가능한 작업과 결정이 필요한 작업을 구분한다. 이 문서는 구현 순서와 미정 사항을 관리하며 업무 정책이나 HTTP 계약을 새로 확정하지 않는다.

검토한 FE 자료는 `42-clubs-FE` 저장소의 다음 문서다. 별도 저장소이므로 경로로 출처를 기록한다.

- `docs/BE_REQUIREMENTS.md`: 동아리 상세 정보·권한 검토 요청
- `docs/FE_BE_API_GAP.md`: 2026-10-17 기준 API 대조 결과
- `docs/FEATURE_BACKLOG.md`: 개선·보류 기능과 재검토 조건
- 실행 설정 참고: `docs/CLUB_API_PREVIEW.md`

FE 대조 문서가 참조한 BE 커밋과 검토 당시 BE HEAD는 `3741e81`이다. FE 문서는 로컬 작업본을 읽었으며, 문서에 기재된 FE 기준은 main `93c84ff` 기반이다. 실제 구현 착수 시 양쪽 변경분을 다시 확인한다. FE의 ‘맞음’은 명세와 코드의 대응을 뜻하며 실제 서버 연동 성공이나 운영 정책 확정을 뜻하지 않는다.

BE 기준은 [문서 관리 규칙](../README.md#문서-관리-ssot)에 따라 [도메인](domain-model.md), [ERD](erd.md), [API 명세](api-endpoints.md), 실제 코드와 테스트를 대조한다. [후속 설계](future-design.md)의 ‘확정’도 현재 구현 범위에 자동 편입하지 않는다.

## 미정 사항 처리 규칙

- 애매하거나 출처 간 내용이 충돌하면 기능 구현보다 기록을 먼저 한다. 해당 항목에 의존하지 않는 작업은 진행할 수 있다.
- 미정 항목의 결정 결과는 아래 표에서 빈칸으로 유지한다. 빈칸은 승인·기본값·기능 불필요를 뜻하지 않는다.
- 결정 전에는 추측한 DTO 필드·DB 컬럼·권한·임시 API·가짜 집계값을 추가하지 않는다. 필드명과 null/빈 배열의 의미도 계약 결정 대상이다.
- FE의 미제공 정보 `—` 표시를 유지한다. 미제공 정보와 실제 집계 결과 0을 구분한다.
- 결정되면 결정 결과·근거·일자를 기록하고 기준 문서를 먼저 갱신한다. 이후 상태를 `구현 가능`으로 바꾼다. 구현과 검증 증거가 있어야 `완료`로 바꾼다.
- 상태는 `미정 → 구현 가능 → 구현 중 → 검증 완료`로 관리한다. 도입하지 않기로 결정한 항목은 근거와 함께 `보류`로 기록한다.

## 1단계: 기존 API 연동 검증

새로운 업무 정책이 필요하지 않은 기존 계약 검증부터 진행한다. 실제 오류가 확인되면 기존 계약에 따른 수정인지 정책 변경인지 먼저 구분한다.

| 대상 | 확인 내용 | 완료 증거 |
| --- | --- | --- |
| 동아리·공지·활동·소모임 조회 | 중첩 경로, 공개 범위, 목록/상세 응답, 페이지네이션 | 요청 조건·응답·관련 테스트 결과 |
| 달력·마이페이지 | 전체 페이지 처리, 한국 날짜 경계, 활동/회차 구분, 본인 참가 내역 | FE 연동 시나리오 결과 |
| 글·활동·회차 생성 | 필수값, 첫 회차/다음 회차, 사진 multipart와 조회 URL | 생성 후 조회 결과 |
| 참가·취소 | 마감 경계, 중복·재참가, 정원 동시성, 주최자 제한, 출결 기록 제한 | 관련 통합 테스트 결과 |
| 회원·권한·출결 | 비회원 명단 접근 거절, 주최자 조건, 권한 관리 범위 | 허용·거절 역할별 테스트 결과 |
| 세션·CSRF | 로그인/로그아웃 후 토큰, 세션 쿠키, 인증 실패 응답 | 기존 테스트 및 실행 환경 확인 |

현재 API로 달력 구현이 가능하므로 달력 전용 API는 추가 작업에 넣지 않는다. FE의 모든 화면 로그인 요구만으로 BE 공개 조회를 인증 필수로 변경하지 않는다.

실제 42 로그인은 FE 자료에 따라 후순위로 검증한다. 실행 환경의 `AUTH_SUCCESS_URL`은 FE 해시 라우터의 `/#/auth/callback` 및 실제 포트와 맞추고 `AUTH_ALLOWED_ORIGINS`도 함께 확인한다. 예시는 `http://localhost:5176/#/auth/callback`이며 고정 운영 주소로 간주하지 않는다. 환경변수 변경 시 [환경변수 문서](environment-variables.md)와 `.env.example`을 함께 갱신한다.

## 2단계: 동아리 상세 응답 검토

기존 `GET /api/v1/clubs/{clubId}` 보강을 우선 검토한다. 권장 검토 순서는 회원 수 → 회장 정보 → 공개 연락처 → 최근 참여이며, 각 항목의 결정이 끝나면 독립적으로 착수한다. 아래 구현 방향은 후보이며 확정 계약이 아니다.

| ID | 요청·출처 | 현재 상태와 결정할 질문 | 결정 후 구현 후보 | 상태 | 결정 결과·근거·일자 |
| --- | --- | --- | --- | --- | --- |
| DETAIL-01 | 회원 수 / BE_REQUIREMENTS | 상세 응답에 없음. ACTIVE 부원 집계 여부, 아카이브 동아리 처리, 공개 범위·필드명은? | 회원 명단을 반환하지 않고 DB 집계. 회장 관계와 부원 관계를 별도로 취급 | 미정 | |
| DETAIL-02 | 회장 정보 / BE_REQUIREMENTS | 상세 응답에 없음. 필요한 사용자 정보·공개 범위·필드명·객체/배열 구조는? 복수 회장과 회장 없음은 어떻게 표시하는가? | 공개 목적의 응답 설계. 최고 관리자 전용 회장 API나 기존 사용자 DTO를 그대로 노출하지 않음 | 미정 | |
| DETAIL-03 | 공개 연락처 / BE_REQUIREMENTS | 형식·개수·저장 위치·등록/수정 담당자·입력 경로·삭제 방법은? | 확정된 저장 구조, 입력 방법과 조회 계약을 함께 구현. 개인 계정 연락처 자동 공개 금지 | 미정 | |
| DETAIL-04 | 최근 참여 / BE_REQUIREMENTS | 집계 기간·활동 범위·고유 인원/누적 건수·공개 단위·시간대는? 삭제 활동·주최자·비부원 참석은 포함하는가? 미확인 기록만 있는 경우는 어떻게 표시하는가? | PRESENT 기반 집계용 조회 기능. 필요한 공개 집계만 반환 | 미정 | |

최근 참여 검토 시 추가로 주의할 점:

- CONFIRMED는 참가 신청 확정이며 실제 참석을 뜻하지 않는다. UNCHECKED는 결석이나 활동 부족으로 해석하지 않는다.
- 현재 출결은 개최 전에도 기록할 수 있으므로 미래 활동 제외 여부와 집계 기준 시각을 결정한다.
- 최근 참여를 [후속 설계의 90일 활동도](future-design.md#활동도-계산), 평가 점수나 활동 등급으로 대체하지 않는다.
- 집계 구현 시 기능별 조회 서비스 경계를 지키고, 공개 요청에서 회원/참가자 명단 전체를 불러와 가공하는 방식은 피한다. 실제 성능에 따라 쿼리·인덱스를 검토하며 미리 스키마를 확장하지 않는다.

## 3단계: 권한 정책 검토

현재 API의 SUPER_ADMIN 전용 권한 관리를 유지하면서 아래 결정을 기록한다. FE 잠정 관리 화면을 최종 운영 정책으로 해석하지 않는다.

| ID | 출처 | 결정할 질문 | 결정 전 처리 | 상태 | 결정 결과·근거·일자 |
| --- | --- | --- | --- | --- | --- |
| AUTHZ-01 | BE_REQUIREMENTS | 업무상 기관 운영자는 BE ADMIN과 같은가? 역할별 업무 범위는? | 역할 자동 매핑·확대 없음 | 미정 | |
| AUTHZ-02 | BE_REQUIREMENTS | 회장 지정 담당자와 지정·회수 절차는? 어떤 사용자/회장 조회 정보가 필요한가? | 기존 SUPER_ADMIN 전용 계약 유지 | 미정 | |
| AUTHZ-03 | BE_REQUIREMENTS | 운영자가 다른 운영자를 지정·해제할 수 있는가? 허용 시 제한과 절차는? | ADMIN의 권한 부여·회수 추가 없음 | 미정 | |

회장 지정과 부원 등록은 별개이며 복수 회장을 지원하는 현행 관계를 유지한다. 최고 관리자 자체 지정·회수 API는 이번 요청에서 추가하지 않는다. 정책 변경이 확정되면 사용자 검색 응답·역할 필터·회장 목록·권한 변경 API 및 관련 권한 응답과 테스트를 함께 검토한다.

## 4단계: 개선·보류 기능의 재검토 조건

아래 항목은 FEATURE_BACKLOG와 FE_BE_API_GAP의 요청 후보다. 표에 있다는 이유만으로 구현 일정이나 계약을 확정하지 않는다.

| ID | 기능 | 착수 전 결정할 내용 | 상태 | 결정 결과·근거·일자 |
| --- | --- | --- | --- | --- |
| EXT-01 | 소모임 전용 공지 | 작성 권한·조회 대상·공개 범위, 동아리/운영 공지와의 구분 | 미정 | |
| EXT-02 | 동아리 활동 참가 자격 선택 | 동아리 기본값/활동별 설정, 설정 권한, 변경 시 기존 참가 처리, 서버 자격 검사 | 미정 | |
| EXT-03 | 신청 메모·주최자 승인 | 선택적 참가 방식, 메모 열람·보존, 대기/확정·정원·취소·재신청 규칙 | 미정 | |
| EXT-04 | 동아리/소모임 정보·글 수정 | 대상별 수정 필드·권한, 일정·정원·마감 변경이 기존 참가에 미치는 영향 | 미정 | |
| EXT-05 | 공지 삭제 | 동아리/운영 공지별 권한, 기록 보존, 목록·상세 처리, 복구 여부 | 미정 | |
| EXT-06 | 수동 모집 마감 | 입부 모집/활동 참가 모집 중 대상, 조기 마감·재개 권한, 기존 신청·취소 허용 범위 | 미정 | |

기존 후속 설계를 채택할 때도 이번 요구와 충돌하는지 대조한다. 특히 동아리 공지 삭제 권한을 운영 공지에 그대로 적용하지 않으며, 입부 모집 마감과 활동 참가 모집 마감을 혼용하지 않는다.

해시 라우터 변경과 모바일 전수 확인은 FE 작업으로 관리하고, 목업은 FE의 시연 대안으로 유지한다. BE가 목업 상태를 실제 사용자·권한으로 신뢰하는 기능은 이 계획에 포함하지 않는다.

## 구현·검증·문서 반영 절차

1. 해당 ID의 질문에 대한 결정을 기록하고 영향 범위를 확인한다. 미정 질문이 구현에 영향을 주면 착수하지 않는다.
2. 도메인 → 필요한 ERD 변경 → API 계약 순서로 기준 문서를 갱신한다. 후속 설계를 채택하면 중복 정책을 남기지 않는다.
3. 필요한 신규 Flyway 마이그레이션·코드·테스트를 구현한다. 기존 적용 마이그레이션을 수정하지 않는다.
4. 권한의 허용/거절, 복수/없음, 0/미제공, 시간 경계, 집계 포함/제외 등 해당 기능의 실제 위험을 검증한다.
5. 코드 변경은 `./gradlew build`로 검증하고 FE 요청·응답을 확인한다. 문서만 변경하면 링크와 기준 문서의 일관성을 확인한다.
6. 기능 ID별 구현 파일·검증 명령과 결과·FE 연동 결과·커밋을 기록한다. 테스트 통과와 실제 연동 확인은 별도로 구분한다.
7. [협업 규칙](../AGENTS.md)에 따라 관련 변경만 기능·정책 단위로 커밋하고 develop에 push한다.

작성 시점에 인증·환경변수·CI 관련 기존 미커밋 작업이 있다. 착수 시 작업 트리와 최신 develop을 확인하고 해당 작업과 무관한 변경을 보존하며, 이 계획의 커밋에 섞지 않는다.
