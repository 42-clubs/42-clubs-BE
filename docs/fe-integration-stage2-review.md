# 동아리 상세 확장 검토 기록

작성일: 2026-10-17. 대상: [구현 계획 2단계](fe-integration-plan.md#2단계-동아리-상세-응답-검토).

이 문서는 검토·구현 영향을 기록한다. 아래 제안은 사용자 결정 전까지 HTTP 계약이나 업무 정책으로 간주하지 않는다. 결정된 내용의 기준은 [도메인](domain-model.md)과 [API 명세](api-endpoints.md)로 옮기고 여기는 결정 근거·검증 결과를 남긴다.

## 재대조 결과

- 최초 검토는 BE `7e890dc` 작업본 기준이며, 회장 공개 범위 승인 후 `6294d85` 작업본에서 재대조했다. FE `docs/BE_REQUIREMENTS.md`·`FE_BE_API_GAP.md` 및 `PublicClubDetailPage.tsx`를 읽었다. 기존 인증·환경변수·CI 미커밋 작업은 별도 작업으로 유지한다.
- FE 상세의 회장·공개 연락처·전체 회원·최근 참여는 여전히 `—`로 표시하며 실제 DTO에도 새 계약이 없다. 서버 필드 추가만으로 화면 표시가 자동 바뀌지는 않는다.
- 최초 BE 공개 명세는 관리자·사용자 정보를 포함하지 않았다. 2026-10-17 사용자 승인에 따라 회장 로그인명·표시 이름만 공개하도록 도메인·API 명세를 갱신했다.
- `club_members`는 ACTIVE/LEFT 관계, `club_managers`는 복수 회장 관계를 보유한다. 두 관계는 독립적이다. 회원 수와 회장 조회는 기존 테이블로 구현 가능하며 신규 저장 컬럼·마이그레이션이 필요하지 않다.
- 회장 사용자 정보는 user 소유 기능의 서비스를 통해 일괄 조회한다. club에서 UserRepository를 직접 호출하거나 최고 관리자 전용 HTTP API를 우회 호출하지 않는다.
- 현재 상세 조회는 공개이므로 필드를 추가하면 비로그인에도 노출된다. FE가 로그인 후에만 화면을 표시하는 것과 별개다.

## 부원·회장 관계와 회원 수 논의

현재 구조의 기준은 [도메인의 부원 관계](domain-model.md#동아리-가입-관계--확정), [회장 관계](domain-model.md#clubmanager-규칙--확정), [ERD](erd.md)다. 사용자는 ACTIVE만 집계하는 방향에 긍정적 의견을 주었지만, 먼저 관계와 집계 기준을 설명해 달라고 요청했다. 따라서 `memberCount`의 공개 계약은 아직 구현하지 않는다.

| 저장 상태 | 현재 의미 | ACTIVE 부원 수로 집계한다면 |
| --- | --- | --- |
| users만 존재 | 서비스 계정은 있으나 해당 동아리 미가입 | 제외 |
| club_members ACTIVE | 현재 가입 중인 부원 | 1명 |
| club_members LEFT | 과거 가입 관계가 남은 탈퇴 상태. 미가입과 구분 | 제외 |
| club_managers만 존재 | 회장 권한만 있음. 자동으로 부원이 되지는 않음 | 제외 |
| club_members ACTIVE와 club_managers 둘 다 존재 | 부원이면서 회장 | 중복 없이 1명 |

`User.role`의 USER/ADMIN/SUPER_ADMIN은 전역 운영 역할이며 회장 지위는 `club_managers` 관계로 표현한다. 회장 지정·회수는 해당 관리 관계만 변경하고 부원 가입·탈퇴를 처리하지 않는다. 부원 등록은 ADMIN·SUPER_ADMIN의 별도 직접 등록이며 신청 대기 상태는 없다. 현재 개인 탈퇴·아카이브 실행 API는 없지만 LEFT 상태를 저장할 구조와 재가입 처리 방식은 준비돼 있다.

Club.operation_status의 ACTIVE/ARCHIVED와 ClubMember.status의 ACTIVE/LEFT는 서로 다른 상태다. 후속 아카이브 일괄 탈퇴 기능은 아직 없으므로 아카이브 동아리라도 저장된 ACTIVE 부원 관계가 자동 제거됐다고 가정하지 않는다. 공개 회원 수에 아카이브를 어떻게 반영할지는 최종 계약에서 명시한다.

## 공개 연락처 미정 사항

현재 `clubs`에는 이름·소개·운영 상태·입부 모집 안내만 있고 별도 공개 연락처 컬럼이 없다. `application_method`와 `application_url`은 입부 지원 안내용이며 공개 연락처로 자동 재사용하지 않는다. FE 목업에 있는 연락처 값도 BE 저장 정보가 아니다.

- 질문: 연락처 종류·허용 형식·복수 여부, 공개 범위, 입력·수정·제거 담당자, 길이·URL 검증 기준, 미등록 표시를 결정해야 한다.
- 영향: 저장 필드가 정해지면 ERD·신규 Flyway가 필요하다. 입력 경로가 API이면 요청 DTO·권한·검증·테스트와 FE 입력 UI도 필요하며, 초기 DB 입력이면 초기 데이터 절차가 필요하다.
- 2026-10-17 사용자 요청대로 질문과 구현 영향만 기록한다. 저장 컬럼·임시 contact 필드·연락처 입력 API를 추가하지 않는다. 최근 참여도 기존 미정 상태를 유지한다.

초기 신규 테스트의 JSON Map 비교가 Spring 테스트의 예상 타입 변환 때문에 실패해, Map 자체를 비교하는 matcher로 수정했다. 실제 응답 값이나 공개 정책을 바꾼 오류 수정은 아니다.

BE 검증은 기존 인증·환경변수·CI 미커밋 작업이 있는 작업본에서 실행했으며 해당 변경은 이번 커밋에서 제외한다. 기존 실행 중인 Compose는 재시작하지 않았고 실제 HTTP 검증은 분리된 Testcontainers DB·임시 서버에서 실행했다. 배포 실행본에 적용하려면 새 코드로 재빌드·재시작이 필요하다.

재실행 가능한 테스트 코드는 [공개 상세 통합 테스트](../src/test/java/com/clubplatform/club/ClubQueryIntegrationTests.java)와 [FE 함수 HTTP 검증](../scripts/verification/fe-live.mjs)에 있다. 로컬 결과는 `build/reports/tests/test/`, `build/reports/tests/feLiveTest/`, `/private/tmp/clubs-stage2-final.log`에서 확인하며 로그는 후속 실행으로 덮어써질 수 있다. 최종 상태는 BE 범위 완료·FE 화면 미완료이므로 DETAIL-02 전체 상태는 `구현 중`으로 유지한다.
