# 동아리 상세 확장 검토 기록

작성일: 2026-10-17. 대상: [구현 계획 2단계](fe-integration-plan.md#2단계-동아리-상세-응답-검토).

이 문서는 검토·구현 영향을 기록한다. 아래 제안은 사용자 결정 전까지 HTTP 계약이나 업무 정책으로 간주하지 않는다. 결정된 내용의 기준은 [도메인](domain-model.md)과 [API 명세](api-endpoints.md)로 옮기고 여기는 결정 근거·검증 결과를 남긴다.

## 재대조 결과

- BE `7e890dc` 작업본과 FE `docs/BE_REQUIREMENTS.md`·`FE_BE_API_GAP.md` 및 `PublicClubDetailPage.tsx`를 다시 읽었다. 기존 인증·환경변수·CI 미커밋 작업은 별도 작업으로 유지한다.
- FE 상세의 회장·공개 연락처·전체 회원·최근 참여는 여전히 `—`로 표시하며 실제 DTO에도 새 계약이 없다. 서버 필드 추가만으로 화면 표시가 자동 바뀌지는 않는다.
- 현재 BE 공개 명세는 관리자·사용자 정보를 포함하지 않는다고 명시한다. 회장 정보 공개는 기존 명세 변경이므로 공개할 정보와 범위를 결정해야 한다.
- `club_members`는 ACTIVE/LEFT 관계, `club_managers`는 복수 회장 관계를 보유한다. 두 관계는 독립적이다. 회원 수와 회장 조회는 기존 테이블로 구현 가능하며 신규 저장 컬럼·마이그레이션이 필요하지 않다.
- 회장 사용자 정보는 user 소유 기능의 서비스를 통해 일괄 조회한다. club에서 UserRepository를 직접 호출하거나 최고 관리자 전용 HTTP API를 우회 호출하지 않는다.
- 현재 상세 조회는 공개이므로 필드를 추가하면 비로그인에도 노출된다. FE가 로그인 후에만 화면을 표시하는 것과 별개다.

## 구현 시 검증할 조건

| 항목 | 검증 조건 |
| --- | --- |
| 회원 수 | 0명·여러 명, ACTIVE/LEFT 제외 조건, 다른 동아리 제외, 회장만 존재/회장 겸 부원 구분, ARCHIVED 동아리, 가입·재가입 후 반영 |
| 회장 정보 | 0명·1명·복수, 동아리 소속 일치, 지정/회수 즉시 반영, 사용자 표시 정보 갱신 반영, 결정한 필드만 공개 |
| 기존 계약 | 비로그인 상세200·없는 상세404, 기존 모집 응답, 목록 필드와 페이지네이션 유지, 관리자 전용 조회·부원 명단 권한 유지 |
| FE 연결 | 확정된 응답 계약 전달 후 FE의 타입·상세 표시가 필요한지 확인. 실제 화면 연결 전에는 BE 구현과 FE 화면 검증을 구분 |

연락처·최근 참여의 구체적인 입력·집계 기대값은 정책 결정 후에 작성한다. 기술 검토만으로 `검토 완료`나 `구현 가능`으로 바꾸지 않는다.
