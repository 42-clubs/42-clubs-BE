# 동아리 상세 확장 검토 기록

작성일: 2026-10-17. 대상: [구현 계획 2단계](fe-integration-plan.md#2단계-동아리-상세-응답-검토).

이 문서는 검토·구현 영향을 기록한다. 아래 제안은 사용자 결정 전까지 HTTP 계약이나 업무 정책으로 간주하지 않는다. 결정된 내용의 기준은 [도메인](domain-model.md)과 [API 명세](api-endpoints.md)로 옮기고 여기는 결정 근거·검증 결과를 남긴다.

## 재대조 결과

- 최초 검토는 BE `7e890dc` 작업본 기준이며, 회장 공개 범위 승인 후 `6294d85` 작업본에서 재대조했다. FE `docs/BE_REQUIREMENTS.md`·`FE_BE_API_GAP.md` 및 `PublicClubDetailPage.tsx`를 읽었다. 기존 인증·환경변수·CI 미커밋 작업은 별도 작업으로 유지한다.
- FE 상세의 회장·공개 연락처·전체 회원·최근 참여는 여전히 `—`로 표시하며 실제 DTO에도 새 계약이 없다. 서버 필드 추가만으로 화면 표시가 자동 바뀌지는 않는다.
- 최초 BE 공개 명세는 관리자·사용자 정보를 포함하지 않았다. 2026-10-17 사용자 승인에 따라 회장 로그인명·표시 이름만 공개하도록 도메인·API 명세를 갱신했다.
- `club_members`는 ACTIVE/LEFT 관계, `club_managers`는 복수 회장 관계를 보유한다. 두 관계는 독립적이다. 회원 수와 회장 조회는 기존 테이블로 구현 가능하며 신규 저장 컬럼·마이그레이션이 필요하지 않다.
- 회장 사용자 정보는 user 소유 기능의 서비스를 통해 일괄 조회한다. club에서 UserRepository를 직접 호출하거나 ADMIN 전용 HTTP API를 우회 호출하지 않는다.
- 현재 상세 조회는 공개이므로 필드를 추가하면 비로그인에도 노출된다. FE가 로그인 후에만 화면을 표시하는 것과 별개다.

## 부원·회장 관계와 회원 수 논의

현재 구조의 기준은 [도메인의 부원 관계](domain-model.md#동아리-가입-관계--확정), [회장 관계](domain-model.md#clubmanager-규칙--확정), [ERD](erd.md)다. 관계 설명 후 사용자는 회원 수에 회장을 포함하도록 결정했다. 아래 표가 확정 기준이며, 이전의 ACTIVE 부원만 집계하는 제안을 대체한다.

| 저장 상태 | 현재 의미 | 회장 포함 memberCount 집계 |
| --- | --- | --- |
| users만 존재 | 서비스 계정은 있으나 해당 동아리 미가입 | 제외 |
| club_members ACTIVE | 현재 가입 중인 부원 | 1명 |
| club_members LEFT, 회장 관계 없음 | 과거 가입 관계가 남은 탈퇴 상태. 미가입과 구분 | 제외 |
| club_managers만 존재 | 회장 권한만 있음. 자동으로 부원이 되지는 않음 | 1명 |
| club_members ACTIVE와 club_managers 둘 다 존재 | 부원이면서 회장 | 중복 없이 1명 |
| club_members LEFT와 club_managers 둘 다 존재 | 부원 상태는 LEFT이나 현재 회장 권한이 있음 | 1명 |

`User.role`의 USER/ADMIN은 전역 운영 역할이며 회장 지위는 `club_managers` 관계로 표현한다. 회장 지정·회수는 해당 관리 관계만 변경하고 부원 가입·탈퇴를 처리하지 않는다. 부원 등록은 ADMIN의 별도 직접 등록이며 신청 대기 상태는 없다. 현재 개인 탈퇴·아카이브 실행 API는 없지만 LEFT 상태를 저장할 구조와 재가입 처리 방식은 준비돼 있다.

Club.operation_status의 ACTIVE/ARCHIVED와 ClubMember.status의 ACTIVE/LEFT는 서로 다른 상태다. 후속 아카이브 일괄 탈퇴 기능은 아직 없으므로 아카이브 동아리라도 저장된 ACTIVE 부원 관계가 자동 제거됐다고 가정하지 않는다. 두 동아리 상태에 동일한 합집합 집계 기준을 적용한다. 조회 과정에서 부원·회장 관계를 생성하거나 변경하지 않는다.

## 공개 연락처 미제공 결정

현재 `clubs`에는 이름·소개·운영 상태·입부 모집 안내만 있고 별도 공개 연락처 컬럼이 없다. `application_method`와 `application_url`은 입부 지원 안내용이며 공개 연락처로 자동 재사용하지 않는다. FE 목업에 있는 연락처 값도 BE 저장 정보가 아니다.

- 2026-10-17 사용자는 질문·영향 기록 이후 공개 연락처를 제공하지 않기로 결정했다. 정책 미정·자료 미등록·API 구현 누락과 구분하며 이번 구현 대상에서 제외한다.
- 저장 컬럼·임시 contact 필드·연락처 입력 API를 추가하지 않는다. 기존 FE의 `—` 표시는 서버의 새 연락처 필드가 생길 예정이라는 뜻으로 해석하지 않는다. FE에서 항목 제거 여부를 별도로 반영해야 한다.
- 재도입 요청이 생길 때만 과거 검토 질문인 종류·형식·복수 여부·공개 범위·입력 담당자·미등록 표시와 스키마/입력 API 영향을 다시 검토한다. 최근 활동의 후속 합의는 아래 별도 기록을 따른다.

## 회장 포함 회원 수 구현·검증 결과

2026-10-17 사용자의 후속 결정에 따라 DETAIL-01의 BE 구현과 검증을 완료했다. ClubMemberRepository의 단일 DB 집계 쿼리에서 ACTIVE 부원 user_id와 현재 회장 user_id를 UNION으로 합쳐 중복을 제거하고 count를 반환한다. 명단이나 사용자 전체를 메모리로 불러오지 않으며 신규 저장 컬럼·마이그레이션·환경변수는 없다.

- 같은 재실행 명령의 `build`에서 기본 테스트166개가 모두 통과했다(실패/오류/skip 0). 새 테스트는 ACTIVE·ARCHIVED 양쪽에서 0명, 일반 부원, 회장만 존재, 부원 겸 회장, LEFT인 현재 회장, 회장 아닌 LEFT, 다른 동아리 제외를 검증한다.
- 부원인 회장의 권한 회수는 인원 수를 줄이지 않고 회장만인 사용자의 권한 회수는 인원 수를 줄이는 것을 확인했다. 재가입·LEFT 전환 후 재조회도 확인했으며 조회가 부원 관계를 자동 생성하지 않는 것을 검증했다.
- FE 함수의 실제 HTTP 검증은 9개 묶음·API 요청127건이 통과했다. 회장만 있는 동아리의 1명, 부원 추가 후 2명, 그 부원을 회장으로 지정해도 2명 유지, 공개 연락처 필드 없음 등을 확인했다.
- 기존 부원 명단·관리 권한 테스트는 그대로 통과했다. FE 상세의 회원 수/회장 표시는 아직 연결되지 않았으며, BE와 실제 HTTP 범위 완료를 FE 화면 완료로 계산하지 않는다.

보고서는 기존 Gradle 보고서 경로와 `/private/tmp/clubs-members-count-final.log`에서 확인한다. 기존 실행 중인 Compose 및 FE 파일을 변경하지 않았으며 새 실행본 반영은 재빌드·재시작이 필요하다. 이 검증 당시 연락처는 구현 대상에서 제외됐고 최근 참여는 미정이었으며, 이후 합의는 다음 절에 반영했다.

## 최근 활동·공개 출석 인원 합의와 검증

2026-10-17 사용자는 누적 집계 대신 가장 최근 활동1개, 제목·개최 시각·신청 확정 인원·주최자를 포함한 PRESENT 인원을 제공하고 개인 명단은 공개 요약에 넣지 않는 방향으로 합의했다. 기준 정책은 [도메인](domain-model.md#최근-활동과-공개-출석-인원--2026-10-17-확정), 필드 계약은 [API 명세](api-endpoints.md#상세-요청)를 따른다.

- 최근 활동은 startsAt <= 서버 현재 시각인 미삭제 동아리 활동 중 시작 시각·ID 내림차순 1개이며 소모임과 미래 활동은 제외한다. 현재 활동에는 종료 시각이 없어 시작한 활동을 기준으로 하며 종료 완료를 뜻하지 않는다. 회장·회원 수와 동일하게 ACTIVE·ARCHIVED에 적용한다.
- 동아리 상세에는 `recentActivity`로 활동 ID·제목·개최 시각·`currentParticipantCount`·`presentParticipantCount`를 제공한다. 대상이 없으면 null, 대상이 있고 전원 미확인이면 출석 확인0이다.
- 동아리 활동 목록·상세에도 `presentParticipantCount`를 추가한다. 두 집계는 CONFIRMED를 기준으로 하고 주최자도 PRESENT 기록이 있을 때 출석 인원으로 센다. CANCELLED는 제외한다. 두 수의 차이는 결석이 아닌 출석 미확인이다.
- 개인 명단은 공개 응답에 추가하지 않고 기존 활동별 주최자 전용 명단·출결 권한을 유지한다. 출석률·누적 참석 건수·마이페이지·소모임 회차 계약은 확장하지 않는다.

`activity`가 이미 club 권한 서비스를 사용하므로 club 조회 서비스에서 activity를 다시 호출하지 않는다. 기존 상세 HTTP 경로는 유지하고 `clubdetail` 조합 계층이 각 소유 서비스의 결과를 합친다. 최근 활동 선택·목록의 일괄 인원 집계는 `ActivitySummaryQueryService`가 소유한다. 기존 인덱스·테이블로 구현하며 마이그레이션·환경변수 변경은 없다. [아키텍처](architecture.md#동아리-상세와-최근-활동-조회-구성)와 [모듈 가이드](module-development.md#실제-구현-동아리-공개-조회)를 동기화했다.
