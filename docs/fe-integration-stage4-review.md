# FE 연동 4단계: 확장 후보 검토

2026-10-17 착수. BE `49f91cd`와 현재 작업본, FE의 `docs/BE_REQUIREMENTS.md`·`docs/FE_BE_API_GAP.md`·`docs/FEATURE_BACKLOG.md`를 읽기 전용으로 대조했다. 사용자 요청으로 프론트는 일체 수정하지 않는다. 기존 OAuth·환경변수 미커밋 작업도 보존한다.

이 단계는 후보별 도입·보류와 세부 정책을 결정하는 단계다. 사용자와 합의되지 않은 기능·API·DB 필드를 먼저 만들지 않는다. [후속 설계](future-design.md)의 ‘확정’도 현재 구현 대상으로 자동 채택하지 않는다. 기준은 [도메인](domain-model.md), [ERD](erd.md), [API 명세](api-endpoints.md)다.

| --- | --- | --- | --- | --- |
| EXT-01 | 소모임 전용 공지 | 동아리 공지와 전체 운영 공지만 제공 | 추가 구현 없음. FE도 소모임 공지 미조회 합의 | 미도입 확정. 사용자 합의 2026-10-17 |

빈칸은 미정이다. FE의 보류 목록에 있었다는 이유만으로 이번에도 보류로 결정하지 않는다. 2단계의 연락처 미제공과 3단계의 USER/ADMIN 통합 정책은 유지한다.

## EXT-05: 공지 삭제 — 우선 검토

### 현재 코드와 기존 설계의 차이

- 동아리 공지는 `NoticeController`의 생성·목록·상세, 운영 공지는 `AnnouncementController`의 생성·목록·상세만 제공한다. 삭제 API는 없다.
- notices(V5)와 announcements(V9)에는 이미 `deleted_at`이 있고 각 Repository는 삭제된 공지를 목록·상세에서 제외한다. 테스트에서 직접 삭제 시각을 넣어 조회 차단을 검증한 상태다. 이는 삭제 실행·권한 검증 완료와는 다르다.
- 현재 동아리 공지 작성은 ACTIVE 동아리의 현재 회장 또는 ADMIN, 운영 공지 작성은 ADMIN에게 허용한다. 회장·부원·전역 역할은 별개다.
- 기존 [후속 삭제 설계](future-design.md#활동공지-삭제와-기록-보존--확정)는 동아리 공지를 현재 회장만 삭제하고 ADMIN도 회장 관계를 요구한다. 현재 작성 권한과 차이가 있으므로 삭제에도 작성 권한을 적용할지는 재합의해야 한다.
- 후속 설계는 ARCHIVED 동아리의 글 삭제 금지, 논리 삭제·복원 미제공을 제시한다. 전체 운영 공지는 동아리에 속하지 않으므로 동아리 운영 상태 규칙을 그대로 적용할 수 없다. 운영 공지 삭제 권한도 별도로 결정한다.

### 사용자에게 확인한 정책 질문

아래 질문은 답변받은 항목만 확정으로 기록한다. 나머지는 **제안이며 결정 결과가 아니다**. 구현에 필요한 답변이 모이기 전에는 도메인·API의 현행 계약이나 기능 코드를 변경하지 않는다.

| 질문 | 제안·선택지 | 결정 결과 |
| --- | --- | --- |
| DELETE-01 삭제 권한 | 동아리 공지는 현재 회장 또는 ADMIN / 현재 회장만. 운영 공지는 모든 ADMIN. 최초 작성자 여부로 권한을 유지하지 않음 | 동아리 공지는 현재 회장 또는 ADMIN, 운영 공지는 ADMIN. 사용자 합의 2026-10-17 |
| DELETE-02 기록·조회·복원·재요청 | DB 행·본문·작성자 보존, deleted_at 기록, 목록 제외·상세 404, 복원·자동 영구 삭제 미제공, 보존 기간은 기존 미정 유지. 권한 있는 반복 삭제 204·처음부터 없는 대상 404 제안 | |
| DELETE-03 아카이브 | 삭제 금지 / ADMIN만 허용 / 현재 회장 또는 ADMIN 허용 | |

복원을 요구하면 삭제 완료 뒤 조회·복원 자격, 아카이브에서 복원 가능 여부, 재삭제 시각 처리까지 추가 논의한다. 보존 기간을 임의로 정하거나 자동 파기 작업을 만들지 않는다.

### 합의 뒤 구현할 범위와 완료 조건

정책 질문이 해결되면 삭제 실행을 두 공지 기능에 각각 연결한다. 기존 삭제 시각 컬럼으로 요구를 충족하는지 먼저 확인하고, 단순 논리 삭제에 불필요한 신규 컬럼·상태를 추가하지 않는다. 스키마 변경 여부와 정확한 HTTP 계약은 채택 범위에 맞춰 기록한다.

| 시나리오 | 사전에 정의할 기대 결과 |
| --- | --- |
| 허용된 사용자의 삭제 | 합의한 성공 응답. 해당 공지의 최초 삭제 시각 기록, 물리 행·본문·작성자·최초 작성 시각 보존 |
| 공개·비공개 동아리 공지 삭제 | 두 공개 범위 모두 일반 목록·상세에서 제외. 페이지 totalElements·totalPages도 삭제 후 데이터 기준 |
| 운영 공지 삭제 | 운영 공지 목록·상세에서 제외하며 동아리 공지는 변경하지 않음 |
| USER·비로그인·CSRF 누락 | 기존 인증·CSRF 계약에 따라 거절하고 삭제 시각을 변경하지 않음 |
| 다른 동아리 회장, 회수된 회장·ADMIN, 이전 작성자 | 현재 권한과 DELETE-01에 따라 허용·거절. 작성자였다는 이유만으로 허용하지 않음 |
| 다른 clubId에 속한 noticeId | 404, 원래 동아리 공지는 변경하지 않음 |
| ARCHIVED 동아리 | DELETE-03에 따른 결과. 거절하면 공지 행 유지 |
| 없는 ID·잘못된 ID·삭제 재요청 | 합의한 404·400·반복 성공 계약. 비인가 재요청으로 삭제 여부를 알아내지 못하도록 권한 검사 유지 |
| 같은 공지의 동시 삭제 | 합의한 반복 요청 계약. 최초 삭제 시각을 덮어쓰지 않으며 부분 반영 없음 |
| 2·3단계 회귀 | 공개 회원 수·회장·최근 활동, ADMIN·회장·주최자·부원 권한 조건을 변경하지 않음 |

API 문서·업무 정책·필요한 ERD 반영, 정상·거절·경계 테스트 및 `./gradlew build` 통과 뒤 BE 구현 완료로 표시한다. FE 수정은 제외하며 버튼·캐시·화면 반영은 별도 미검증으로 기록한다. 활동·소모임 삭제와 삭제된 활동의 참가 내역 열람은 이번 공지 삭제에 자동 포함하지 않는다.

## 나머지 후보의 논의 지점

### EXT-01 소모임 전용 공지 — 미도입 확정

- 결정·사유: 소모임에서는 별도 공지까지 제공할 필요가 없다는 사용자 판단에 따라 소모임 전용 공지를 도입하지 않는다(2026-10-17). 일시 보류나 구현 대기 항목으로 남기지 않는다.
- BE 범위: 소모임·회차에 귀속된 공지 작성·목록·상세 API와 저장 구조를 추가하지 않는다. 현재 공지는 동아리 공지(`notices.club_id`)와 전체 운영 공지(`announcements`)를 유지한다.
- FE 합의: 소모임에 대한 공지 조회를 하지 않는다. 이는 사용자에게 전달받은 합의 내용이며 이번 작업에서 FE 파일을 수정하거나 실제 FE 화면을 검증했다는 뜻은 아니다.
- 검토 종료: 미정이었던 소모임 공지의 작성 권한·열람 자격·공개 범위는 이번 구현에서 결정할 필요가 없다. 별도의 기능 도입 요청이 있을 때만 범위·권한부터 다시 검토한다.
- 확인: 현재 소모임 작성·조회 컨트롤러와 현행 API 명세에 소모임 전용 공지가 없는 것을 대조했다. 기능 코드·DB·환경변수 변경은 없다. 동아리·운영 공지 삭제(EXT-05)는 별도 검토를 계속한다.

### EXT-02 동아리 활동 참가 자격 선택

- 현재 `ActivityParticipationService.join`은 로그인·모집 시간·중복·정원을 검사하며 해당 동아리 가입 여부는 검사하지 않는다. 활동 생성 시 회장인 주최자가 자동 CONFIRMED 참가한다.
- 동아리 공통 설정인지 활동별 설정인지, 변경 담당자가 현재 회장인지 주최자인지 ADMIN도 포함하는지 정해야 한다.
- ‘부원만’의 부원은 ACTIVE ClubMember만인지, 회원 수 집계처럼 현재 회장도 포함하는지 별도 결정이다. 회장 관계만 있고 부원 관계가 없는 주최자의 자동 참가도 다뤄야 한다. 공개 회원 수 정책이 참가 자격까지 확장되지는 않는다.
- 모집 중 자격을 좁힐 때 이미 참가한 비부원을 유지·취소·변경 금지 중 어떻게 처리할지, LEFT 전환 이후 기존 참가·재신청은 어떻게 할지 정해야 한다.
- 도입 시 기존 활동의 기본값·마이그레이션을 정하고 비부원·LEFT·회장만인 사용자·다른 동아리 부원과 자격 변경/신청 동시 요청을 검증한다. 자격 설정과 부원 가입을 자동 연결하지 않는다.

### EXT-03 신청 메모·주최자 승인

- 현재 활동·소모임 회차 참가 테이블은 CONFIRMED/CANCELLED 두 상태만 허용하고 메모 컬럼·승인 API가 없다. 정원·출석·마이페이지는 현재 CONFIRMED를 기준으로 한다.
- 대상이 동아리 활동인지 소모임 회차인지 둘 다인지, 메모만 먼저 도입할지 승인 방식과 함께 도입할지 결정한다. 후속 설계의 소모임 승인제를 동아리 활동에도 적용한다고 간주하지 않는다.
- 메모 필수 여부·길이·열람자·재신청 시 덮어쓰기·취소 뒤 보존, 승인 가능 시각·담당자, PENDING의 정원 예약 여부, 거절·취소·재신청·방식 변경을 정해야 한다.
- 기존 후속 설계의 ‘PENDING은 자리 미예약·승인 때 정원 확인’은 채택할 수 있는 안이다. 승인 대기를 빈자리 대기열로 해석하지 않는다.
- 도입 시 상태 CHECK·조회·내 신청 상태·대기 목록·개인정보 노출·동시 승인과 정원을 함께 검증한다. 대기자를 출석이나 공개 확정 인원에 임의로 포함하지 않는다.

### EXT-04 정보·글 수정

한 번에 하나의 수정 기능으로 취급하지 않고 아래 대상을 나눠 채택한다. 현재 어느 대상에도 수정 API가 없다.

| 대상 | 결정할 필드·권한·기존 데이터 영향 |
| --- | --- |
| 동아리 기본 정보 | 이름·요약·소개 중 허용 필드, 현재 회장/ADMIN 범위, ARCHIVED 제한. 연락처 미제공 합의는 유지 |
| 동아리·운영 공지 | 제목·본문·공개 범위 변경, 현재 권한과 이전 작성자의 차이, 비공개 전환 이후 조회 |
| 동아리 활동 | 제목·본문·사진과 일정·정원을 분리. 신청 이후 일정 변경, 확정 인원보다 작은 정원, 주최자 변경의 별도 여부 |
| 소모임 기본 글 | 모임 제목·소개 수정이 기존 회차 제목·일정에 미치는 영향, 해당 주최자의 권한 |
| 소모임 회차 | 제목·시작/종료·마감·장소·정원 중 허용 필드, 지난 회차·참가자 존재 시 제한, 생성 시 최소 2시간 규칙의 수정 시 적용 여부 |

- 기존 후속 설계는 일부 현재 회장·아카이브 제한만 정리했으며 필드별 변경·참가자 처리는 미정이다. ADMIN 통합만으로 수정 권한이 생기지는 않는다.
- 사진 교체를 도입하면 기존 저장소·업로드 실패 정리·삭제된 파일 조회를 함께 설계한다. 부분 수정에서 생략과 null의 의미, 동시 참가·수정 중 정원/일정의 일관성도 정해야 한다.
- 수정된 개최 시각은 공개 최근 활동 선택과 달력·대표 회차·진행 상태에 영향을 준다. 생성 검증을 그대로 재사용해 지난 글의 오탈자 수정까지 막지 않도록 범위를 구분한다.

### EXT-06 수동 모집 마감

먼저 ‘모집’ 대상을 정해야 한다. 같은 마감 버튼으로 합치지 않는다.

- 활동·회차는 현재 모집 마감에 도달하면 참가·재참가뿐 아니라 본인 취소도 거절한다. 조기 마감에도 이 취소 제한을 적용할지가 핵심 질문이다.
- 기존 확정 참가·출결을 모집 마감만으로 취소하지는 않는 안을 검토하되 최종 결정은 따로 기록한다. 미래 회차 전체 취소·개최 취소는 별도 범위다.
- 참가·취소 검증 외에도 응답의 recruiting·목록 정렬·모집 중 표시가 같은 기준을 사용해야 한다. 도입 시 마감/재개와 참가가 경쟁하는 요청 및 원래 마감·개최 시각 경계를 검증한다.
