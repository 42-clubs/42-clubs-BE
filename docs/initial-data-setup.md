# 초기 동아리·회장·최고 관리자 입력

MVP 0단계 운영 절차입니다. 스키마는 [ERD](erd.md), 권한 정책은 [도메인](domain-model.md#초기-등록과-최고-관리자--확정)을 따릅니다. 실제 계정·동아리 정보는 Flyway나 저장소에 넣지 않습니다.

## 준비

1. 대상 DB를 확인하고 기존 데이터가 있으면 백업합니다. 애플리케이션을 먼저 시작해 Flyway V3까지 적용하고 종료하거나 초기 입력 중 로그인·운영 쓰기를 중지합니다.
2. 운영자가 받은 동아리 이름·소개, 최고 관리자와 회장의 **42 숫자 ID**·로그인명·표시 이름을 확인합니다. 계정의 경산 소속도 확인합니다. 로그인명으로 계정을 연결하거나 숫자 ID를 추측하지 않습니다.
3. [SQL 틀](../scripts/db/bootstrap-initial-data.sql)을 검토하고, 저장소 밖의 접근 제한된 작업 폴더에 psql 변수 파일을 작성합니다. 비밀번호는 변수 파일·명령행·커밋에 넣지 않고 psql 프롬프트 또는 보호된 `.pgpass`를 사용합니다.

변수 파일에는 아래 이름을 모두 지정합니다. 다음은 **치환 전 형식**이며 그대로 실행하지 않습니다. 실제 값은 로컬 비공개 파일에서만 채웁니다.

```sql
\set club_name '동아리 이름'
\set club_summary '200자 이내 소개'
\set club_description '상세 소개'
\set super_intra_id '확인한 양수 42 숫자 ID'
\set super_login '확인한 최고 관리자 로그인명'
\set super_name '최고 관리자 표시 이름'
\set manager_intra_id '확인한 양수 42 숫자 ID'
\set manager_login '확인한 회장 로그인명'
\set manager_name '회장 표시 이름'
```

로그인명·표시 이름·동아리 이름은 비어 있지 않은 100자 이내 값입니다. SQL 변수에 작은따옴표나 백슬래시를 입력할 때는 psql의 문자열 이스케이프 규칙을 따릅니다. 틀은 `:'변수명'`으로 값을 SQL 문자열 리터럴로 인용합니다. DB 연결 환경변수는 [기존 환경변수 문서](environment-variables.md#데이터베이스)를 참고합니다. 새 애플리케이션 환경변수는 없습니다.

## 실행

저장소 루트에서 PostgreSQL 클라이언트 `psql`로 실행합니다. 아래 호스트·계정·DB 이름은 기본 로컬 Compose 예시이므로 **대상 환경에 맞춰 확인**합니다.

```sh
psql -X -h 127.0.0.1 -p 5432 -U clubs -d clubs -W \
  -v ON_ERROR_STOP=1 \
  -f /absolute/private/path/initial-data-vars.sql \
  -f scripts/db/bootstrap-initial-data.sql
```

`BEGIN`부터 `COMMIT`까지 동아리·사용자·회장 관계를 함께 입력합니다. 오류가 나면 `ON_ERROR_STOP`으로 실행이 중단되고 연결 종료 시 트랜잭션 전체가 롤백됩니다. 수동 대화형 실행 중 오류가 발생하면 `ROLLBACK` 후 원인을 수정합니다. 성공하면 출력되는 내부 사용자 ID·동아리 ID·역할·회장 관계를 확인합니다.

- `users.id`는 DB가 생성하는 내부 PK입니다. 사용자 입력은 UNIQUE `intra_id` 기준으로 기존 행을 갱신하고 내부 ID·생성 시각을 유지합니다. 최고 관리자는 SUPER_ADMIN으로 지정하며 회장은 신규 USER로 생성하거나 기존 역할을 유지합니다. 같은 사용자가 두 역할을 맡아도 SUPER_ADMIN이 유지됩니다.
- 동아리 이름은 스키마상 UNIQUE가 아닙니다. 초기 입력 틀은 동아리 쓰기를 잠그고 이름으로 대상 하나를 찾습니다. 같은 이름이 여러 개면 실패하므로 기존 동아리 ID를 확인해 중복 이름을 정리하거나, 별도 검토한 ID 지정 SQL을 사용합니다. 기존 동아리가 하나면 소개·상태·모집 설정을 변경하지 않습니다.
- 같은 값으로 재실행하면 사용자·동아리·회장 관계가 중복되지 않습니다. 동아리 이름을 바꾸어 실행하면 새 동아리를 만들 수 있으므로 실패 재시도 전 입력과 DB를 다시 확인합니다.
- 여러 동아리·회장은 같은 최고 관리자 정보와 각각의 동아리·회장 정보로 반복 입력할 수 있습니다. 회장이 없는 동아리는 검토한 동아리 INSERT만 실행합니다. 틀의 회장 계정을 임의로 채워 넣지 않습니다.
- 회장 관계는 전역 ADMIN 권한이나 부원 관계를 자동 생성하지 않습니다. SUPER_ADMIN도 해당 동아리 회장 관계 없이 활동·공지를 작성할 수 없습니다.

## 로그인 확인과 이후 운영

1. 최고 관리자와 회장이 기존 42 OAuth로 로그인합니다. 숫자 `intra_id`가 같으면 초기 행의 내부 ID·역할·생성 시각을 보존하고 최신 로그인명·표시 이름만 동기화합니다. 새 숫자 ID로 로그인한 계정은 USER이며 OAuth 프로필로 높은 역할을 얻지 못합니다.
2. `/api/v1/me`의 내부 ID와 role을 확인합니다. SUPER_ADMIN은 ADMIN 운영 권한도 갖지만 회장·주최자·부원 관계 조건을 우회하지 않습니다. 권한 변경은 기존 세션의 다음 요청부터 반영됩니다.
3. 입력에 쓴 비공개 파일은 조직의 보관 정책에 따라 처리하고 저장소·공용 로그에 첨부하지 않습니다.

초기 DB 지정 이후 ADMIN·회장 권한 변경은 구현된 [1단계 API](mvp-implementation-plan.md#1-사용자-검색최고-관리자-권한-관리)를 사용합니다. SUPER_ADMIN 자체 부여·회수는 일반 API에 노출하지 않으며 별도 운영자 DB 절차로 관리합니다.
