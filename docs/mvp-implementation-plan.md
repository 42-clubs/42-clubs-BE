# MVP 기능별 엔드포인트 구현 계획

상태: 0~7단계 구현 완료 (2026-10-16). 업무 API 34개를 모두 구현했습니다. 실제 AWS·42 자격증명·프론트엔드 연결과 운영 초기 데이터 입력은 환경별 확인 사항입니다. 이 문서는 작업 순서·의존성·완료 조건을 관리합니다. 경로와 권한의 기준은 [API 명세](api-endpoints.md), 업무 정책은 [도메인](domain-model.md), 테이블 정의는 [ERD](erd.md)입니다. 경로는 `/api/v1` 접두사를 생략합니다.

## 범위와 순서

기존 인증·동아리 공개 조회 7개는 유지합니다. 신규 API 총 34개를 모두 구현했습니다. 활동 사진은 작성 요청에 포함하므로 별도 업로드 API를 추가하지 않습니다. 같은 메서드·경로의 검색 필터는 별도 API로 세지 않습니다.

| 순서 | 기능 | 신규 API | 선행 작업 |
| --- | --- | ---: | --- |
| 0 | 역할·권한 기반, 초기 DB 입력 절차 (완료) | 0 | 기존 인증 |
| 1 | 사용자 검색·최고 관리자 권한 관리 (완료) | 6 | 0 |
| 2 | 부원 등록·현황·명단 (완료) | 3 | 1 |
| 3 | 동아리·운영 공지 작성·조회 (완료) | 6 | 0 |
| 4 | 동아리 활동 작성·조회 (완료) | 3 | 0, 사진 저장소·조회 방식 확정 |
| 5 | 활동 참가·취소·기본 출결 (완료) | 5 | 4 |
| 6 | 소모임·회차 작성·조회 (완료) | 6 | 0, 회차 표시 계약 확정 |
| 7 | 회차 참가·취소·기본 출결 (완료) | 5 | 6, 5의 동시성 처리 검증 |

권장 진행 순서는 0 → 1 → 2 → 3 → 4 → 5 → 6 → 7입니다. 사용자 검색은 최고 관리자 화면에서도 필요하므로 기존 부원 관리 묶음에서 1단계로 앞당깁니다. 사진 저장소는 기본 로컬 디스크이며 공개 사진 조회 API를 제공합니다. S3는 선택 설정으로 유지합니다.

## 0. 역할·권한 기반과 초기 데이터

**상태: 구현 완료 (2026-10-14)**

- V3에서 SUPER_ADMIN 역할 CHECK와 club_managers·유니크 제약·FK·동아리별 인덱스를 추가했습니다. 기존 V1·V2는 유지합니다.
- enum·세션 권한·SecurityConfig를 동기화하고 ACTIVE 동아리의 현재 회장 관계를 검사하는 `ClubPermissionService.requireManager`를 구현했습니다. 신규 운영·작성 API는 각 후속 단계에서 연결합니다.
- [초기 DB 입력 절차](initial-data-setup.md)와 [트랜잭션 SQL 틀](../scripts/db/bootstrap-initial-data.sql)을 준비했습니다. 실제 사용자 정보는 포함하지 않았습니다.
- `./gradlew build` 성공, PostgreSQL·OAuth·HTTP 회귀를 포함한 59개 테스트 통과(생략 없음). 초기 행의 intra_id·내부 ID·역할 보존, OAuth 역할 위조 거절, 기존 세션의 역할·회장 권한 회수 반영, SUPER_ADMIN의 ADMIN 운영 권한 포함·회장 관계 우회 거절, 유니크·FK·롤백·재실행을 검증했습니다.

**작업**

- 새 Flyway 마이그레이션으로 `users.role`의 CHECK에 SUPER_ADMIN을 추가하고 enum·세션 사용자 권한·SecurityConfig를 동기화합니다. 이미 적용된 V1은 수정하지 않습니다.
- `club_managers` 테이블과 동아리별 회장 권한 검사를 구현합니다. SUPER_ADMIN은 ADMIN 운영 기능과 공지 관리를 포함합니다. 활동 작성의 회장·참가 명단과 출결의 주최자·부원 명단 조건은 유지합니다.
- `users.id`는 내부 PK, 숫자 `intra_id`는 UNIQUE 계정 연결 키, `intra_login`은 표시·검색 값으로 현재 구조를 유지합니다. 로그인명을 PK로 바꾸는 작업은 포함하지 않습니다.
- 운영자가 받은 초기 동아리·회장·최고 관리자 정보를 DB에 입력하는 실행 절차와 트랜잭션 SQL 틀을 준비합니다. 실제 사용자 데이터는 공용 마이그레이션·저장소에 넣지 않습니다.
- 초기 사용자 입력 시 로그인 동기화가 같은 `intra_id` 행을 사용하고 지정된 역할을 유지하는지 확인합니다. 초기 DB 지정 이후 권한 변경은 1단계 API를 사용합니다.

**완료 조건**

기존 OAuth·CSRF·로그아웃·동아리 조회가 유지되고 SUPER_ADMIN으로 ADMIN 운영 API를 호출할 수 있습니다. 일반 로그인으로 SUPER_ADMIN을 얻을 수 없으며 역할 회수는 기존 세션의 다음 요청부터 반영됩니다.

## 1. 사용자 검색·최고 관리자 권한 관리

**상태: 구현 완료 (2026-10-16)**

- 사용자 검색·ADMIN 변경은 user, 회장 목록·변경은 club 서비스가 담당합니다. 기능 간 사용자 조회·역할 검사는 user의 서비스 계약으로 호출합니다.
- 역할별 DTO·검색·페이지네이션·204 반복 변경·409 최고 관리자 보호 계약은 [API 명세](api-endpoints.md#사용자-검색권한-관리--구현-계약)에 반영했습니다.
- 기존 V1~V3 스키마를 사용하며 새 마이그레이션·환경변수는 없습니다. 사용자/동아리 행 잠금과 기존 유니크 제약으로 동시 변경을 보호합니다.
- PostgreSQL·MockMvc 통합 테스트 24개로 역할별 6개 API 접근, CSRF, 검색·페이지·DTO, 최고 관리자 보호, 기존 세션 회수 반영, 동아리 격리와 동시 부여·회수를 검증했습니다. 기존 미커밋 로그인 디버깅 변경을 제외한 임시 체크아웃에서 `./gradlew build --offline` 성공, 전체 97개 테스트 통과(실패·생략 없음). 원래 작업 디렉터리에서도 빌드와 98개 테스트가 통과했습니다.
- 실제 42 자격증명·프론트엔드 연동과 운영 초기 데이터 입력은 별도 환경 확인 사항입니다.

| 메서드 | 경로 | 목적 |
| --- | --- | --- |
| GET | /admin/users | intraLogin으로 사용자 검색, SUPER_ADMIN의 role=ADMIN 필터 조회 |
| PUT | /admin/users/{userId}/admin-role | ADMIN 부여 |
| DELETE | /admin/users/{userId}/admin-role | ADMIN 회수 |
| GET | /admin/clubs/{clubId}/managers | 회장 목록 |
| PUT | /admin/clubs/{clubId}/managers/{userId} | 회장 권한 부여 |
| DELETE | /admin/clubs/{clubId}/managers/{userId} | 회장 권한 회수 |

**작업**

사용자 검색은 ADMIN·SUPER_ADMIN이 이용하고 역할 필터·역할 정보는 SUPER_ADMIN 계약으로 분리합니다. 나머지 5개는 SUPER_ADMIN 전용입니다. 검색 일치 방식·페이지네이션·역할별 응답 DTO를 API 계약으로 고정했습니다. 역할 변경은 `users`, 회장 지정은 `club_managers`에 반영하고 부원 관계를 자동 생성하지 않습니다.

**검증·완료 조건**

일반 ADMIN의 권한 부여·회수 시도는 403입니다. SUPER_ADMIN 대상 강등은 거절합니다. 반복 부여·회수는 중복 관계를 만들지 않고, 대상 없는 요청과 다른 동아리 관계 접근을 검증합니다. 권한 회수 후 작성 권한은 즉시 사라지며 기존 글·참가 기록·부원 관계는 유지됩니다.

## 2. 부원 등록·현황·명단

**상태: 구현 완료 (2026-10-16)**

| 메서드 | 경로 | 목적 |
| --- | --- | --- |
| GET | /admin/users/{userId}/clubs | 현재 가입 동아리와 가입 수 |
| PUT | /admin/clubs/{clubId}/members/{userId} | 직접 등록·재등록 |
| GET | /clubs/{clubId}/members | ACTIVE 부원 명단 |

**작업**

`club_members` 마이그레이션·엔티티·Repository와 등록 유스케이스를 구현합니다. 1단계 검색으로 선택한 사용자의 가입 현황을 표시하고 운영자가 등록합니다. ACTIVE 등록의 반복은 동일 관계를 유지하고 LEFT의 재등록은 기존 관계를 갱신합니다. 최대 2개 가입 정책은 운영자 확인용이며 서버가 가입 수로 자동 차단하지 않습니다.

**검증·완료 조건**

ADMIN·SUPER_ADMIN만 등록하고 대상 동아리는 ACTIVE여야 합니다. 명단은 해당 동아리 ACTIVE 부원만 볼 수 있습니다. 회장·최고 관리자라는 이유만으로 명단이 노출되지 않으며 중복 등록·동시 등록에서도 관계는 하나입니다. 가입 신청·탈퇴 API는 추가하지 않습니다.

## 4. 동아리 활동 작성·조회

**상태: 구현 완료 (2026-10-16)**

| 메서드 | 경로 | 목적 |
| --- | --- | --- |
| POST | /clubs/{clubId}/activities | 회장의 활동 작성 |
| GET | /clubs/{clubId}/activities | 활동 목록 |
| GET | /clubs/{clubId}/activities/{activityId} | 활동 상세 |

**확정한 구현**

사진의 선택 첨부·파일 제한·백엔드 경유 업로드·별도 파일 저장소 보관·이미지 URL 제공·실패 정리 원칙은 [도메인](domain-model.md#활동-사진--확정), multipart·대표 이미지 응답은 [API 계약](api-endpoints.md#활동-사진-요청응답-계약)으로 확정했습니다. 기본 저장소는 로컬 디스크, 조회는 백엔드 사진 URL입니다. S3 선택 시 이미지 도메인 또는 15분 만료 서명 GET URL을 사용합니다. 업로드 저널과 저널 행 잠금으로 실패 파일 정리를 재시도합니다. 프론트엔드 기본 이미지 자산은 연동 환경에서 확인합니다. 사진 없이 등록할 수 있어도 첨부 기능을 빼고 활동 기능 전체를 완료로 처리하지 않습니다.

**작업**

`activities`·`activity_images`와 `activity_participants`를 생성합니다. 참가 테이블은 주최자 자동 참가 때문에 이 단계부터 필요합니다. author_id와 organizer_id는 작성한 회장으로 고정하고 활동·주최자 CONFIRMED 참가를 같은 트랜잭션에 저장합니다. 정원은 주최자를 포함합니다. 개최·모집 마감 일시와 정원을 검증하고 모집 중 우선 정렬·현재 참가 수·D-Day 응답을 구현합니다.

**검증·완료 조건**

다른 사용자를 주최자로 지정할 수 없습니다. 정원 1일 때 주최자만으로 정원이 차고, 모집 마감이 개최 이상이면 생성이 실패합니다. 실패 시 활동·주최자 참가가 일부만 남지 않아야 합니다. 사진 없이 등록·빈 사진 목록·기본 이미지 표시 계약, 첫 사진의 대표 이미지 선택, 응답 URL을 통한 이미지 조회, 파일 제한·실제 이미지 검증, 업로드/DB 실패 시 파일 정리·정리 실패 기록을 검증합니다. 정렬 후 페이지네이션·공개 응답의 참가 명단 제외도 확인합니다.

## 5. 활동 참가·취소·기본 출결

**상태: 구현 완료 (2026-10-16)**

| 메서드 | 경로 | 목적 |
| --- | --- | --- |
| POST | /clubs/{clubId}/activities/{activityId}/participants | 본인 참가·재참가 |
| DELETE | /clubs/{clubId}/activities/{activityId}/participants/me | 본인 참가 취소 |
| GET | /clubs/{clubId}/activities/{activityId}/participants/me | 본인 참가·출결 상태 |
| GET | /clubs/{clubId}/activities/{activityId}/participants | 주최자의 참가자·출결 명단 |
| PATCH | /clubs/{clubId}/activities/{activityId}/participants/{userId}/attendance | 주최자의 출결 기록 |

**작업**

활동 행의 비관적 쓰기 잠금으로 참가 가능 검사·CONFIRMED 수 집계·참가 저장을 같은 트랜잭션으로 처리합니다. 사용자별 유니크 제약과 취소 후 재참가를 함께 구현합니다. 미참가 본인 상태는 status·attendanceStatus 모두 null이며 충돌 오류 코드는 [API 계약](api-endpoints.md#활동소모임-구현-계약)에 고정했습니다. 출결은 UNCHECKED/PRESENT만 받고 체크 사용자·시각을 서버가 기록합니다.

**검증·완료 조건**

마지막 한 자리에 동시에 신청해도 정원을 넘지 않습니다. 마감 직전에는 참가·취소가 가능하고 정확히 마감부터 불가능합니다. 주최자 취소, 다른 사람을 대신한 신청, 출결이 남은 관계의 재참가를 거절합니다. CONFIRMED 참가자만 출석 처리하며 UNCHECKED 복귀 시 체크 정보를 비웁니다. 다른 회장·ADMIN·SUPER_ADMIN의 출결 접근도 주최자가 아니면 거절합니다.

| POST | /gatherings/{gatheringId}/sessions | 같은 모임에 다음 회차 생성 |
| GET | /gatherings/{gatheringId}/sessions | 예정·지난 회차 목록 |
| GET | /gatherings/{gatheringId}/sessions/{sessionId} | 회차 상세 |

**확정한 구현**

즉시 모집 공개로 구현했습니다. 대표 회차는 진행 중 → 가장 가까운 예정 → 가장 최근 지난 회차이며 UPCOMING/ONGOING/PAST 필터를 제공합니다. 기본 이미지는 프론트 공통 자산입니다. 세부 경계와 정렬은 [도메인 구현 세부 계약](domain-model.md#mvp-구현-세부-계약)을 따릅니다.

**작업**

`gatherings`·`gathering_sessions`·`gathering_session_participants`를 생성합니다. 생성자는 세션에서 정하고 모임·첫 회차·주최자 참가를 원자적으로 저장합니다. 후속 회차는 기존 모임 주최자만 생성하며 회차·주최자 참가를 함께 저장합니다. 공개 상세와 회차 목록을 조합할 수 있도록 생성 응답에 gatheringId·sessionId를 제공합니다.

**검증·완료 조건**

한 회차 생성 실패 시 부분 데이터가 남지 않습니다. 후속 회차는 같은 gatheringId와 새 sessionId를 가지며 이전 참가자·출결을 복사하지 않습니다. 다른 주최자는 회차를 추가할 수 없습니다. 일회성·정기형 모두 같은 구조로 화면에 표시하고 자동 반복 기능은 만들지 않습니다.

## 7. 회차 참가·취소·기본 출결

**상태: 구현 완료 (2026-10-16)**

| 메서드 | 경로 | 목적 |
| --- | --- | --- |
| POST | /gatherings/{gatheringId}/sessions/{sessionId}/participants | 본인 참가·재참가 |
| DELETE | /gatherings/{gatheringId}/sessions/{sessionId}/participants/me | 본인 참가 취소 |
| GET | /gatherings/{gatheringId}/sessions/{sessionId}/participants/me | 본인 참가·출결 상태 |
| GET | /gatherings/{gatheringId}/sessions/{sessionId}/participants | 주최자의 회차 참가자·출결 명단 |
| PATCH | /gatherings/{gatheringId}/sessions/{sessionId}/participants/{userId}/attendance | 주최자의 회차 출결 기록 |

**작업**

5단계에서 검증한 참가·취소·출결 규칙을 회차 단위로 구현합니다. 활동과 공통인 검증을 재사용할 수 있지만 별도 테이블·서비스 경계는 유지합니다. 공통 모임 인터페이스나 엔티티 상속은 선행 작업으로 두지 않습니다.

**검증·완료 조건**

5단계의 정원 경쟁·마감 경계·본인 식별·출결 권한 검증에 더해, 같은 사용자가 여러 회차에 독립적으로 참가할 수 있는지 확인합니다. 한 회차의 취소·출결 변경은 다른 회차에 영향을 주지 않아야 합니다. 모임의 고정 부원 관계는 생성하지 않습니다.

## 기능별 공통 완료 기준
